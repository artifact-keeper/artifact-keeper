---
section: Fixed
issues: [#4146, #4059]
---
- **Conda's `notices.json` was the one conda read surface with no visibility check of its own, and concurrent withdrawals silently lost notices** (#4146, #4059). Every other conda read path — `channeldata.json`, each `repodata` variant and encoding, `run_exports.json`, package download — resolves the repository and then calls `check_read_access`. `notices.json` never did. While it returned a hard-coded `{"notices": []}` the omission cost nothing; since per-package withdrawal landed it carries data, one notice per withdrawn package naming the filename and quoting the administrator's reason verbatim, which is the embargoed-advisory and vendor-reported-malware text the feature exists to publish. The handler now takes the same gate in the same position, before any notice is read, and the token-URL form (`/conda/t/{token}/{repo}/notices.json`) binds the auth extension it previously did not take.

  **No disclosure was reachable on a deployed instance, and no action is needed on upgrade.** Every conda route, token URLs included, is mounted under `repo_visibility_middleware`, which resolves the repository and decides the read before any handler runs. Measured through the production router against the pre-fix handler on a private channel holding a withdrawal notice: an anonymous caller received `401 Authentication required` and an authenticated principal with no role assignment on the repository received `404 Repository not found` — byte-identical to what `channeldata.json` returned to those same two callers, and with neither the reason nor the withdrawn filename in the body. Only a repository member read the notice, which is the intended behaviour. What changes is that the endpoint no longer depends solely on the middleware for a decision the rest of the channel makes twice, so it cannot answer differently from its siblings if it is ever reached by a route mounted outside that layer.

  **Appending a notice was an unguarded read-modify-write**, spread across three statements on separate pooled connections, and this one was reachable: two withdrawals in flight at once — a vendor advisory naming a batch of packages is exactly that case — kept only the later writer's notice, silently, while both requests returned 200 with their own `notice_id`. Eight concurrent withdrawals against the pre-fix code left six notices. The append is now one transaction that takes a row lock on the `repository_config` row before reading it, appends, and writes back. The lock is taken by an upsert whose conflict arm rewrites the existing value rather than by a bare `SELECT ... FOR UPDATE`, because on a channel's first withdrawal there is no row to lock yet and two first withdrawals would otherwise still race on the INSERT. The stored CEP-6 notice shape is unchanged, the `value` column stays `TEXT` so no migration is required, and a missing or corrupt blob is still tolerated as an empty list rather than becoming a 500 on a client-facing endpoint.
