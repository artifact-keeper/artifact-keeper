- **Webhook fetch-by-id now requires the same read-carrying grant as the webhook listing, and repository-scoped tokens confine admins consistently** (#3901). `GET /api/v1/webhooks/{id}` and its deliveries endpoint admitted any non-empty fine-grained grant, so a `{write}`-only grantee refused the webhook in the listing was still served its URL, headers and secret metadata by id; the by-id path now asks for `RepoAccess::READ`, and the listing's role arm carries the same `read` capability, so a custom role without `read`/`admin` neither lists nor fetches the webhook (built-in roles all carry `read`). Webhook reads (`GET /webhooks`, `GET /webhooks/{id}`, its deliveries) now also require the `read:repositories` token scope, and the custom `headers` in every read response have their values redacted to `***` — they usually carry the receiver's bearer token, and the signing secret was already digest-only. Separately, the packages listing and the repository listing evaluated `is_admin` before the token's repository scope, letting an admin with a repository-scoped token enumerate everything; the scope now binds first, matching search and the webhook reads.
