- **Scan-on-proxy now gates proxied NuGet, Chocolatey and PowerShell packages** (#4102, part of #4097). With scan-on-proxy enabled on a Remote `nuget`, `chocolatey` or `powershell` repository, every `.nupkg` it proxies goes through the shared inline gate, on both the V3 flat container (`/v3/flatcontainer/{id}/{version}/{file}`) and the legacy V2 route (`/v2/package/{id}/{version}`) that Chocolatey and `nuget.exe` use, whichever protocol the upstream speaks. A vulnerable package is refused with `403 scan_blocked`. A clean one is served with `X-AK-Scan: clean`, and its verdict is reused on the next pull, from either route. Fail-open (`X-AK-Scan: pending`), fail-closed (`423`), record-only (`X-AK-Scan: recorded`) and the severity threshold behave as they do for the other enforced formats. The package's identity is taken from the requested id and version and pinned only when its own `.nuspec` agrees (ids compared case-insensitively, versions in NuGet's normalized form, so a `.nuspec` saying `1.0` matches a flat-container `1.0.0`). A package that declares a different coordinate is treated as inconclusive. The `.nuspec` manifest itself passes unscanned. On a Virtual repository each Remote member is scanned under the stricter of the virtual's and the member's policy, and a member's `403`/`409`/`423` ends the walk instead of falling through to the next member; a hosted member ahead of a scanning remote still serves first. A Remote package row whose stored blob is missing and that records no digest is now repaired through the gate too. On Remote and Virtual NuGet repositories (whether or not scan-on-proxy is on), a package id, version or file name containing `/`, `\`, `?`, `#`, `;`, `%`, a space or a control character after decoding, ending in `.`, or equal to `..`, is now refused with `400`: such a coordinate let the version-list route fetch a `.nupkg` from upstream and serve it unscanned. `GET /api/v1/formats` now reports `nuget` as `scan_on_proxy: "enforced"`.
