- **Scan-on-proxy now gates proxied NuGet, Chocolatey and PowerShell packages** (#4102, part of #4097). With scan-on-proxy enabled on a Remote `nuget`, `chocolatey` or `powershell` repository, every `.nupkg` it proxies goes through the shared inline gate, on both the V3 flat container (`/v3/flatcontainer/{id}/{version}/{file}`) and the legacy V2 route (`/v2/package/{id}/{version}`) that Chocolatey and `nuget.exe` use, whichever protocol the upstream speaks. A vulnerable package is refused with `403 scan_blocked`. A clean one is served with `X-AK-Scan: clean`, and its verdict is reused on the next pull, from either route. Fail-open (`X-AK-Scan: pending`), fail-closed (`423`), record-only (`X-AK-Scan: recorded`) and the severity threshold behave as they do for the other enforced formats. The package's identity is taken from the requested id and version and pinned only when its own `.nuspec` agrees (ids compared case-insensitively, versions in NuGet's normalized form, so a `.nuspec` saying `1.0` matches a flat-container `1.0.0`). A package that declares a different coordinate is treated as inconclusive. The `.nuspec` manifest itself passes unscanned. A symbols package (`.snupkg`) is scanned without an identity pin, so a vulnerable one is blocked but fail-closed does not withhold it for lacking one. Against a V2 upstream, the flat container now answers only `{id}.{version}.nupkg` and returns `404` for any other file name; it used to answer a `.nuspec` request with the package bytes, which also bypassed the gate. On a Virtual repository each Remote member is scanned under the stricter of the virtual's and the member's policy, and a member's `403`/`409`/`423` ends the walk instead of falling through to the next member; a hosted member ahead of a scanning remote still serves first. A Remote package row whose stored blob is missing is repaired as follows on a scanning repository: with no recorded digest, the re-fetch goes through the gate (and the warm proxy-cache body is no longer copied into the row unscanned); with a recorded SHA-256, a stored `vulnerable` verdict for that digest refuses the pull. On Remote and Virtual NuGet repositories (whether or not scan-on-proxy is on), a package id, version or file name containing `/`, `\`, `?`, `#`, `;`, `%`, a space or a control character after decoding, ending in `.`, or equal to `..`, is now refused with `400`: such a coordinate let the version-list route fetch a `.nupkg` from upstream and serve it unscanned. `GET /api/v1/formats` now reports `nuget` as `scan_on_proxy: "enforced"`. The shared `.nuspec` reader now stops at 4 MiB, because the gate runs it on upstream bytes. It also backs validation and metadata parsing for NuGet packages uploaded through the generic upload endpoint, so such an upload with a larger `.nuspec` is now refused with `400` (`dotnet nuget push` uses its own bounded reader and is unchanged). On the proxy gate an oversized `.nuspec` leaves the package unpinned, i.e. inconclusive.
