- **Kubernetes clusters can pull images with a pod's ServiceAccount token instead of an `imagePullSecret`.** (#1246). Since Kubernetes 1.34 the kubelet can hand an image credential provider a pod-bound ServiceAccount token, and the CI OIDC exchange (`POST /api/v1/auth/ci/token`) now serves as the server side of that. Three additions make it work for real clusters. A CI OIDC provider can carry a **static JWKS** (`key_source: static`, `static_jwks`) and then verifies only against it, never contacting the issuer, so on-prem clusters (kubeadm's `https://kubernetes.default.svc.cluster.local`) and AKS without `--enable-oidc-issuer` work although Artifact Keeper cannot reach them; existing providers become `key_source: discovery` and behave exactly as before. A `claim_filters` key starting with `/` is a **JSON Pointer** into nested claims, so `{"/kubernetes.io/namespace": "payments"}` admits every ServiceAccount of a namespace; keys without a leading `/` keep their meaning, and a malformed pointer is refused with 400 when the mapping is saved. And a new provider type, **`kubernetes`**, changes what an exchange mints. See the Kubernetes section of `docs/ci-oidc.md` for issuers per platform, key rotation and an example CronJob that keeps a static JWKS current.

  Security-relevant behaviour: a **`kubernetes` exchange mints a pull-only credential** (`read:artifacts`, `read:repositories`, whatever the account's groups allow) **and no refresh token**, because the kubelet caches it on a node where root can read it and a leaked push-capable token could replace images for every consumer; the ceiling is fixed by type and cannot be configured wider. Its `security` log line records the pulling workload's namespace, ServiceAccount, pod and node. A **static JWKS is a hand-entered trust anchor**: it accepts public RSA/EC keys only (private members are refused with 400), requires unique `kid`s, refuses a token whose `kid` is not in the set with 401 naming the missing `kid` (no fall-back to another key), and every change to a provider's key source or JWKS is written to the `security` log with the acting admin and the resulting `kid`s. Use a dedicated provider audience, never the API server's own; that is documented, not yet enforced (#4133). The `gitlab`, `github` and `generic` provider types still mint action-unrestricted tokens with a refresh token; action scopes for them are tracked in #4132. Migration 236 adds `key_source` and `static_jwks` to `ci_oidc_providers` with safe defaults. Rolling back leaves the columns unused and makes `kubernetes` providers act as `generic` (unrestricted, renewable tokens), so disable them before rolling back.
