- **Content imported by the Artifactory / Nexus migration tooling before origin tracking existed is now recorded as `migration`, not `hosted`** (#4153). The origin backfill (migration 228) derived every older row from its repository, so imported artifacts were frozen as hosted uploads by the immutability trigger. Migration 270 re-stamps a row as `{"kind":"migration","upstream_url":<source system URL>}` only when all of these hold: a completed, non-dry-run migration item for the same target repository (resolved through the job's `repo_mappings`) carries the row's SHA-256; the row already existed when the item completed; the path is one the importer writes for that item; and only one source system claims it. Anything ambiguous stays `hosted`, and so does an upload that merely shares bytes and file name with an item whose own row exists. While the migration runs, the immutability trigger's function admits exactly this one rewrite, and only on a connection that sets the transaction-local `ak.origin_rewrite` GUC. The strict function is restored at the end. No table lock is taken on `artifacts`. The re-stamp runs in 5000-row batches with a 5-second `lock_timeout` per batch and retries. It reports how many rows it planned and re-stamped, how many rows it left `hosted` because two source systems claim them, and how many items it skipped because their file name matched more than one row. The online-migration gate now requires `lock_timeout` in any new migration that backfills or adds a trigger to a large table, and refuses `DISABLE`/`ENABLE TRIGGER` on one.

  Operator note: no action is needed. To see what changed, compare `SELECT count(*) FROM artifacts WHERE origin->>'kind' = 'migration'` before and after the upgrade. The `migration 270` NOTICE lines are logged under `sqlx::postgres::notice` at INFO, so they appear with the shipped images' `RUST_LOG=info` but not with the built-in default filter.
