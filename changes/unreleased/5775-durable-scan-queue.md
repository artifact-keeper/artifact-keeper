- **Scans can run from a durable Postgres queue, on a separate worker** (#5775). Since #5231 a proxy file scan waits its turn in an in-process table, which one backend process owns: a restart loses whatever was queued or running, a retry that reaches another replica starts the scan again there, and the CVE engine runs on the pods that serve requests. `POST /api/v1/security/scan` also still commits its `scan_results` placeholders and then spawns the scan, so a restart leaves them for the stuck-scan janitor. `SCAN_QUEUE_ENABLED=true` (default `false`) turns both into jobs in a new `scan_queue` table (migration 362). A job carries a reference to the proxy-cached object, never the bytes, and a worker claims it with `FOR UPDATE SKIP LOCKED` under a heartbeaten lease, retries it with backoff and recovers it from a pod that died mid-scan.

  With the queue on, `fail_open` and `record_only` pulls serve as before and queue the scan. A `fail_closed` pull of cached bytes queues its scan ahead of those and waits on its verdict as long as it would on an in-process scan (`AK_PROXY_SCAN_QUEUE_WAIT_SECS` plus the 30-second budget, within three quarters of `GLOBAL_REQUEST_TIMEOUT_SECS`), holding a task rather than a scan permit. A `fail_closed` fresh fill, OCI images, OS packages and catalog-requiring rescans keep the in-process path. `SCAN_WORKER_ENABLED` (default `true`) lets a fleet stop the API pods draining the queue and run the same image as a worker, sized by `SCAN_WORKER_CONCURRENCY`. `GET /api/v1/admin/security/scan-queue` (admin only) lists the queue, and the worker publishes `ak_scan_queue_depth`, `ak_scan_queue_oldest_pending_seconds`, `ak_scan_queue_wait_seconds`, `ak_scan_queue_consumers`, `ak_scan_worker_slots_in_flight`, `ak_scan_worker_slots_capacity`, `ak_scan_jobs_total` and `ak_scan_job_duration_seconds`. With the queue off, nothing changes.
