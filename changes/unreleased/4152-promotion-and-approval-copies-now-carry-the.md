section: Security
issues: [#4152]

- **Promotion and approval copies now carry the source artifact's `origin` instead of re-deriving one for the target repository** (#4152). `artifacts.origin` (#4050) records where an artifact's bytes came from and is immutable once written, but the three copy paths that move content between repositories — single promote, bulk promote and approval-execute — inserted the copy with no `origin` at all, so migration 227's `artifacts_origin_fill` trigger derived a fresh document from the **target** repo and stamped `{"v":1,"kind":"hosted","repository_key":"<target>"}` on it. Promotion is the path most content takes into a serving repository, so the upstream that actually supplied proxied, mirrored or migrated bytes was erased at exactly the hop where it matters: a lower-trust source shadowing a higher-trust one — the attack `origin` exists to make visible — became invisible the moment the artifact was promoted, and `origin ->> 'upstream_url'` (the indexed "which artifacts did this upstream supply?" incident query) stopped naming the copy. All three paths now read the source row's recorded document and write it verbatim onto the copy; the fill trigger already honours an explicitly supplied origin and derives only when the column is NULL, so no schema change was needed and the derivation for a genuine upload is untouched. Copies keep the repository key of first arrival rather than being re-stamped for each hop. Existing rows are not rewritten — `artifacts_origin_immutable` forbids it, and a copy already stamped `hosted` stays that way.
