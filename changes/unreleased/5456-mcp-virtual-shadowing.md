---
section: Security
issues: [#5456]
---
- **An approved MCP server version is pinned to, and held unless it still gets, what its Virtual backing repository actually serves** (#5456). npm, PyPI, NuGet and Cargo packages are installed from `registryBaseUrl`, which is the mapped repository, and a Virtual serves a version from the member its download walk picks. The pin was taken by a plain priority lookup, and nothing rechecked it. So a later publish at the pinned coordinate in a higher-priority member changed what clients downloaded, while the stored pin, the gated rows and the MCP read still said "approved". The same happened when a higher-ranked Remote member fetched the version from its upstream (cached or not), with nested Virtuals, with equal priorities, and for PyPI with other files of the version (another member's wheel, `1.0` spelled for `1.0.0`, or a file uploaded under another project name).

  The pin and the check now walk the same member list as the download route (nested Virtuals expanded, ties broken by key) through the same per-format guards: npm's shadowing guard, isolate mode and scope policy, Cargo's exact-version owner guard, strict priority for NuGet, and every hosted file of the version for PyPI. A publish that a Remote member would serve in place of the hosted package is refused with `422 mcp_package_shadowed`, naming the members and the fixes. A PyPI package is not pinned through a Virtual with a Remote member, which can always serve other distributions of the version. On every read, a version whose route no longer serves the pinned rows is held as `mcp_unresolvable` (`gate: shadowed` for the repository holder). That covers a pinned row whose bytes changed in place. The pin never moves.

  Upgrading: existing approved versions are checked too, so some are held as soon as the upgraded server reads them: those pinned through an npm or NuGet Virtual with a Remote member ranked above the hosted member, and those pinned through a PyPI Virtual with any Remote member that has an upstream. They answer `404` (`mcp_unresolvable`, `gate: shadowed` for the holder) and drop out of listings and `latest`. Re-rank the hosted member above the Remote, enable isolate mode on an npm Virtual, or remove the Remote from a PyPI Virtual, and the hold clears on the next read without a republish. Mapping the hosted repository directly applies only to versions published afterwards. Known caveat: a caller who cannot read the pinned member can still be served another member's bytes at the pinned coordinate (#5536).
