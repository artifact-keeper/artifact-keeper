- **A repository can be made mutable so a re-upload replaces the existing file instead of answering 409** (#5188). Set `mutable: true` on `POST /api/v1/repositories` or `PATCH /api/v1/repositories/{key}` (it is echoed back on every repository response). Snapshot and development channels can then republish under the same version and filename ("latest build wins"), which clients with no overwrite option, such as `twine`, need. The default is `false`, so every existing repository stays write-once.

  The flag is honoured by the direct, streaming and chunked upload paths, by the PyPI upload route, and by the system-package file-drop formats Debian, RPM, Alpine and Pacman (which each enforced their own "Package already exists" 409 at publish time, now gated on the same flag). Alpine and Pacman key their storage by path, so the bytes are overwritten in place and the superseded `artifacts` row is dropped before the new one is inserted; the direct/streaming/chunked, PyPI, RPM and Debian paths publish through the shared upload path, whose `ON CONFLICT DO UPDATE` and immutability oracle handle the replace and hand the old object to storage GC, which deletes it once nothing else references it. On a Generic or Mlmodel repository with `versioning_enabled`, versioning still applies and a re-upload appends a revision instead. Versioned-package formats whose consumers pin coordinates (npm, Cargo, Go, Maven releases, Sbt, Bazel) and the Helm chart upload stay write-once, and OCI tags remain mutable through their own path. Clients that pin hashes (`pip --require-hashes`, `poetry.lock`, `uv.lock`) will reject a replaced file, and a remote repository proxying this one keeps serving the copy it already cached, so reserve the flag for channels whose consumers expect content at a path to change.
