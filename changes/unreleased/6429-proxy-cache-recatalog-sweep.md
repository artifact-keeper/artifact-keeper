- **A background sweep restores the catalog row of a cached proxy file whose row was lost, without waiting for the file to be read again. On by default every 6 hours; set `PROXY_CACHE_RECATALOG_INTERVAL_SECS=0` to turn it off** (#6429). Since #5635 a fill's `proxy_cache_artifacts` row commits asynchronously, so a database crash or failover can lose it while the cached file and its sidecar stay; a failed best-effort catalog write leaves the same state. Until a later read re-cataloged it, the file's bytes were missing from the Remote's usage ledger (quota and the cache cap), from cache-cap eviction and from the periodic re-scan.

  The sweep walks every Remote's cache tree in pages of 1,000 keys (a new bounded listing on the filesystem, S3, GCS and Azure backends), in chunks of `PROXY_CACHE_RECATALOG_BUDGET` keys (100,000) 30 s apart, on one replica at a time under the `proxy_cache_recatalog` scheduler lease. Its position is saved in a new `scheduler_job_cursors` table (migration 415), so a restart or lease handover resumes the walk instead of starting over; a walk of 10 million keys takes about 1.5 hours on a filesystem cache. A Remote whose listing fails is logged, counted and skipped. For a sidecar with no row it writes the row from the sidecar through the read-time backfill's statement, so a row a concurrent fill writes is never overwritten and a held entry keeps its hold. It never reads the cached body. It leaves alone a cached upstream 404, a sidecar whose body is gone or is not the size it records, one younger than `PROXY_CACHE_RECATALOG_MIN_AGE_SECS` (600), one older than its Remote, an entry whose legacy `artifacts` row is in the trash or rejected, and an entry purged while it ran: cache invalidation now deletes the files before the row, and the sweep takes back a row it inserted for an entry that is gone. Each chunk logs one line and counts `ak_proxy_cache_recatalog_total{outcome}` and `ak_proxy_cache_recatalog_bytes_total`.

  Measured with `scripts/perf/proxy-cache-recatalog.sh` (2,000 cached 4 KiB entries in one generic Remote, 200 catalog rows deleted, the files kept, a 10 s interval): on 1.13.0 main the 819,200 bytes stay missing from the ledger for as long as nobody reads those files; with the sweep every row is back 11.6 s after the loss, the ledger equals the live sum and the upstream is not contacted. The restoring pass took 1.6 s; a pass with nothing to restore lists the 4,000 keys in 0.4-0.55 s with one catalog query per 1,000-key page.

  See `docs/operations/proxy-cache-ha.md`.
