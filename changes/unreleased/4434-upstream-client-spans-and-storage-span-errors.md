- **Upstream registry requests now appear in traces as CLIENT spans that carry the trace onward, and failed storage operations mark their spans as errors** (#4434, #3954). Every request the proxy makes to an upstream registry (artifact and metadata fetches including `fetch_upstream_direct`, conditional revalidations, and the OCI bearer-token exchange and its retry) runs in an `otel.kind = client` span named after the HTTP method, with `http.request.method`, `url.full` (credentials, query and fragment removed), `server.address`, `server.port`, `http.response.status_code` and, on failure, `error.type`. The span covers connect, TLS, redirects and the wait for response headers, so upstream latency is now attributable in a trace instead of being an untraced gap. The span's W3C `traceparent`/`tracestate` is injected into the outbound request, so an instrumented upstream continues the same trace. A 4xx or 5xx (other than the `401` bearer challenge an OCI registry sends before the token exchange) or a transport failure sets the span status to error. Injection happens only when OpenTelemetry export is configured (`OTEL_EXPORTER_OTLP_ENDPOINT`), and the trace id sent upstream is the backend's own, which adopts an inbound `traceparent` only from a trusted proxy.

  The filesystem, S3, GCS and Azure storage spans now record the error of a failed operation, which sets the span status to error. The error is recorded as an INFO-level event on the span, so a routine miss (a proxy-cache lookup of an absent key) is visible in the trace without becoming an ERROR log line.
