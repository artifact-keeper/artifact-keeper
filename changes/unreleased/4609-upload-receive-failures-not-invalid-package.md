- **An upload the server could not receive in full is no longer reported as an invalid package** (#4609). The archive-parsing publish routes (conda, RubyGems, npm, Cargo, Composer, Hex, VS Code, Go modules, Alpine, Pacman, CRAN, RPM) took the body through axum's `Bytes` extractor, which answered every receive failure with `400 Failed to buffer the request body` and buffered each body at about twice its size: two concurrent 1.5 GB conda uploads OOM-killed a 4 GiB replica. These routes now receive the body into one buffer of its declared size, charged to a process-wide budget (`UPLOAD_MEMORY_BUDGET_BYTES`, default half the cgroup memory limit), check the received length against `Content-Length`, and only then parse it. A body cut short is `408` with code `incomplete_body`; a full budget or failed allocation is `503` with `Retry-After`; a full scratch or storage disk is `507` with `Retry-After` (previously a bare `500`); other server-side receive or spool failures are `503` with `Retry-After`, logged at `error` with the cause. A `400` now always means the complete package was received and is itself invalid. The shared spooling helpers used by PyPI, NuGet, Maven, Terraform, Swift, Chef and Pub apply the same rules. See `docs/operations/upload-scratch-disk.md`.
