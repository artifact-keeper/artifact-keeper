- **Scan policies can refuse uncataloged artifacts, a repository can treat plain archives as assessed, and one call lists the artifacts behind a repository's coverage** (#4994). `block_uncataloged` on a scan policy (default `false`) refuses, on download (`403`) and promotion (`block-uncataloged`), an artifact whose latest completed scan of some scanner cataloged nothing. `PUT /api/v1/repositories/{key}/security/uncataloged-policy` (instance administrators) sets `uncataloged_policy` to `fail` (default) or `warn`; under `warn` an artifact no scanner could catalog still shows in `coverage.uncataloged` and `has_uncataloged_scan` but no longer keeps the repository from `rated`, so a generic repository of documentation bundles can be rated. There is no `ignore`. `GET /api/v1/repositories/{key}/security/coverage/artifacts` lists the artifacts by coverage status (`failed`, `uncataloged`, `partial` by default; also `cataloged`, `unscanned`) with each one's latest scans and the reason they did not assess it, plus live counts. Migration 361 adds the columns with defaults only, so no existing policy or repository changes outcome (and existing quality gates and promotion rules get `accepted_grade_status: any`, keeping the 1.11 behaviour; see the Changed entry). After the upgrade and a rescan, the coverage listing, `GET /api/v1/security/scores` (`grade_status`) and the gate and rule evaluate endpoints show what tightening a gate would refuse. A 1.11 replica ignores the columns during a rolling upgrade. See docs/security/grade-status.md.
