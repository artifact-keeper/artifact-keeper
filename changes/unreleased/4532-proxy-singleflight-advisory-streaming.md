section: Fixed
issues: [#4532, #4013]
---
- **With `PROXY_SINGLEFLIGHT_ADVISORY_LOCKS_ENABLED=true`, a cold streamed object is fetched upstream once cluster-wide instead of once per request** (#4532, #4013). Before, every request contended for the cross-replica lock, including requests in the leader's own replica. The losers gave up after about 1.6 s and fetched upstream themselves: 200 concurrent GETs of a 256 MiB object across 3 replicas made 94-100 upstream fetches, and the mock upstream answered many of them with 502. Now requests coalesce in-process first, and only one request per replica contends for the lock. A replica that loses waits for the leader to finish and then serves the object, with its waiting requests, from the cache. The leader releases the lock only after its cache entry is published. A woken replica also drops the cache miss it remembered for up to 30 s, so it finds the new entry instead of fetching the object a second time. If the leader is still downloading after `PROXY_SINGLEFLIGHT_LOCK_WAIT_TIMEOUT_SECS` (default 65), each waiting replica fetches the object once itself. That keeps the worst case at one upstream fetch per replica, not one per request. Each waiting replica holds one database connection per cold object while it waits. `PROXY_SINGLEFLIGHT_MAX_LOCK_WAITERS` caps those waits (default 32 per replica; past the cap a replica fetches at once). Keep `PROXY_SINGLEFLIGHT_LOCK_WAIT_TIMEOUT_SECS` below your ingress read timeout. If the leading replica's node is lost mid-download (for example a force-deleted pod), Postgres detects the dead connection through TCP keepalives on the lock session within about 30 s. It then releases the lock, and the waiting replicas re-elect a new leader at once instead of waiting out the full timeout.
