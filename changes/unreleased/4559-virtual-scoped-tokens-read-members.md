section: Changed
issues: [#4559]
---
- **A token scoped to a virtual repository reads the virtual's members through it** (closes #4559). A repository token minted on a virtual repository, or a user token whose `repo_selector` names it, can now read the virtual's members on requests routed through the virtual (the format endpoints such as `/conda/<virtual>/...` and `/pypi/<virtual>/simple/...`, the `/t/<token>/` forms, and the virtual's REST member listing, artifact listing, download and storage total), without its scope naming the members. Before, such a token was refused every member and a virtual conda channel answered `404 Virtual repository has no accessible members`, so a per-repository consumer token could not be issued for the one channel URL consumers use. Each member is still checked against the token owner's grants, so a member the owner cannot read stays out of the listings and indexes and cannot be downloaded through the virtual. A request to a member's own URL with such a token is still refused (404), which keeps per-virtual policies such as the conda package allowlist (#4576) from being bypassed through the member. Writes are unchanged: deploying through a virtual still needs the token's scope to name the hosted member. Scoping a token to the members, or to the virtual and its members, keeps working.
