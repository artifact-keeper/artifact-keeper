- **Group changes and failed HTTP Basic logins are now audited** ([#5653]). Creating, renaming and deleting a group and adding or removing its members wrote no audit row, although a group grants its members every permission rule it holds, so a privilege change through a group left no trail. `POST`/`PUT`/`DELETE /api/v1/groups[/{id}]` now write `GROUP_CREATED`, `GROUP_UPDATED` (name and description before and after) and `GROUP_DELETED` (with the member count that cascaded), and `POST`/`DELETE /api/v1/groups/{id}/members` write `GROUP_MEMBERS_ADDED` / `GROUP_MEMBERS_REMOVED` listing only the users whose membership changed; each names the acting principal and the group (`resource_type: group`). A local password refused on HTTP Basic (package clients, `curl -u`) now writes `LOGIN_FAILED` with `auth_method: basic` and the reason, as a refused `POST /api/v1/auth/login` already did; written by whichever layer answers the request (the guest-access guard for the management API and `/v2`), at most one row per username and source IP per minute per replica with a `suppressed_since_last_row` count, so a client retrying a stale password does not write a row per request. When the LDAP Basic passthrough refuses the credentials its own row stands for the request; it now writes one for every refusal (new reasons `not_directory_account`, `no_directory_provider`, `directory_sync_refused`), and a passthrough attempt the login limiter stops is recorded with `reason: ldap_passthrough_rate_limited`. `POST /api/v1/admin/settings` changes are audited by #5652. Audit rows for alert suppression, health-check runs, storage GC and the cleanup job are not part of this change.
