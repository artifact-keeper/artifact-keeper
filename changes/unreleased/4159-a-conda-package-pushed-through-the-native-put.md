- **A conda package pushed through the native `PUT /conda/{repo}/{subdir}/{filename}` route is now scanned on upload, instead of being stored ungraded until someone remembered to trigger a repository scan** (#4159). The generic upload path gets its scan-on-upload trigger from `ArtifactService::finalize_upload`, which reads the repository's `scan_configs` row and spawns the scan after the artifact row commits. `store_conda_package` never constructs an `ArtifactService` — it writes the `artifacts` row with raw SQL and returns 201 — so a repository with `scan_enabled` and `scan_on_upload` both true produced no `scan_results` row for a natively published conda package, and its repository score stayed null. The purpose-built helper for exactly this, `scanner_service::spawn_scan_on_upload`, had a single production caller (the Incus finalizer) carrying a comment that format-native paths must mirror it; conda now does, with the same config gate, the same non-blocking spawn and the same warn-on-failure logging, placed immediately after the row is committed and the upload hold applied. All four native conda upload entry points (`PUT`, `POST /upload`, and the two token-bearing variants) funnel through that helper, so all four are covered. The download-time policy gate is unaffected — `block_unscanned` already handled the never-scanned artifact — but the grade and the security dashboard now reflect a pushed package without operator action.
