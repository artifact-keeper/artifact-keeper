- **The scanner-adapter can refuse an image too large to scan instead of running trivy into an OOM kill or an eviction** (#5909). trivy downloads every layer of an image into its cache directory and holds the analysed layers in memory, so an image larger than the adapter pod's memory or ephemeral-storage limit got the adapter killed or evicted mid-scan (artifact-keeper-iac#439: a 4.4 GB image against a 1 GiB temp volume), took every other running scan down with it, and was recorded as `failed: Bad gateway`. With the new `SCANNER_MAX_IMAGE_BYTES` set, the adapter reads the image manifest first (for an index, the platform image it would scan) and, when the compressed config and layers add up to more than the limit, ends the job without running trivy: the report route answers `422` with `X-Scan-Status: TooLarge`, and the backend records the scan as failed with the reason `not scanned: image too large: <image> is <n> bytes ..., over SCANNER_MAX_IMAGE_BYTES=<limit>` and does not resubmit it. A manifest the adapter cannot read never blocks a scan. Default `0` keeps today's behaviour (no bound); set it from the pod's memory and ephemeral-storage limits. A filesystem-scan upload over `SCANNER_FS_MAX_UPLOAD_BYTES` is now answered `413` with `not scanned: workspace too large` instead of `400 invalid workspace tar`. The adapter-side change ships in scanner-adapter 1.7.0.
