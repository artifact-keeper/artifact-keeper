section: Fixed
issues: [#5640, #5633]
---
- **Basic `username:<api_token>` is checked as a token first, and invalid tokens answer 401 instead of tripping the auth-capacity 503** ([#5640], [#5633]). A package client sending an API token as the HTTP Basic password (the form the Setup Guide gives for Maven `settings.xml`, and the one pixi/conda and npm `.npmrc` use) first had the token bcrypt-verified as the user's *password* (cost 12, about 0.34 s), recorded as a failed login (`failed_login_attempts`, `locked_until` and `last_failed_login_at` written on every request), and only then tried as a token. That made Basic about 30 times slower than Bearer, saturated the 32-slot auth limiter under any burst so `pixi install` against a conda Virtual aborted on `503 Authentication service is at capacity`, and kept the account flagged as locked. The shape match is exact and anchored: a Basic password that is exactly 41 bytes with `_` at byte 8 and hex digits everywhere else is an API token, and one that is a compact JWS beginning `eyJ` is an Artifact Keeper JWT. On the package/format routes such a password is resolved only as that token. On the management API (`/api/v1`), which never accepts an API token as a Basic password, an API-token-shaped password is refused outright and a JWT-shaped one is checked only as an access token. In both cases there is no bcrypt and no failed-login write. Any other password pays one bcrypt as before, and a wrong one still counts toward the lockout. Separately, an API token whose prefix is unknown, revoked or expired, an expired JWT, and a malformed credential are now rejected before the bcrypt verify, so they never take an auth-capacity permit: a burst of them answers `401`, not a retryable `503` that turned one expired login into a client retry storm. A wrong Basic password for an unknown username now runs the same single bcrypt as one for a real account, so the two take comparable time. The exception is while the LDAP Basic-auth passthrough is enabled: directory users then skip that pad, so their passthrough requests, cached ones included, run no local bcrypt. A local password that is itself shaped exactly like an API token or an Artifact Keeper JWT can no longer be used as a Basic password, on the package routes or on the management API. It still works at `POST /api/v1/auth/login`. Prefer `Authorization: Bearer <api_token>` where the client supports it; see `docs/api-token-expiration-policy.md`.
