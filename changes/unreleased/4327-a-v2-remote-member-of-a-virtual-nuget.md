- **A V2 remote member of a virtual NuGet repository no longer disappears when its upstream answers `index.json` with an error** (#4327). Many V2 servers answer `/index.json` with 400, 401, 403 or 5xx rather than 404. A standalone V2 remote already kept working in that case (#4126), but the same upstream as a virtual repository's member was dropped: its packages were missing from the virtual's V2 feed, and a V2 download through the virtual returned 404. Both now follow the standalone rule: only a positive V3 answer switches to V3, and otherwise the member's own V2 feed is used. The standalone and member downloads share one function, so they cannot drift apart again. Member downloads retain scan-on-proxy enforcement, including a virtual repository's stricter policy; a scan refusal stops the member walk rather than serving the package from a later member. The V3 surface still refuses to fall back to V2 on a probe error, so a transient failure of a real V3 feed is never answered from paths it does not serve.

  A member whose probe fails SLOWLY is still skipped, as before, and its upstream is not asked a second time. The proxy reports "never answered" the same way as "answered 403" and waits 60 seconds before giving up, and members are asked one after another, so falling back after a timeout would double that wait for every V2 request through the virtual repository. That would push a feed past a NuGet client's own timeout where it used to answer, only without the dead member. A failed probe therefore counts as an answer only if it came back within 5 seconds; a real error answer takes milliseconds. This limit applies to virtual members only: a standalone V2 remote keeps falling back after any probe error, as it has since #4126.
