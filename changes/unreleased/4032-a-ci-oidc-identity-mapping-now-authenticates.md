- **A CI OIDC identity mapping now authenticates every branch, tag and matched project as one service account, instead of only the first ref that ever ran** (#4031). `POST /api/v1/auth/ci/token` derived the service-account username from the identity mapping (`ci-<8 hex of the mapping id>`) but looked the account up by the token's `sub`. GitLab's `sub` embeds the ref (`project_path:group/app:ref_type:branch:ref:main`), so the first pipeline to run created the account, and every other branch and every tag failed with **`409 Conflict "Username already exists"`**. A tag-triggered release pipeline broke as soon as a `main` build had run, and the error named neither the mapping nor the cause. The same mismatch had three other effects. Array (any-of) `claim_filters` could never admit a second project. Two mappings whose UUIDs shared their first 8 hex characters could not both have an account. And the account only existed after a successful exchange, so operators had to run the pipeline, let it fail, copy `ci-xxxxxxxx` out of the job log, grant it, and apply their configuration a second time. The account is now keyed on the mapping (`users.external_id = ci:<provider_id>:<mapping_id>`), and the subject is kept only in the display name and the exchange's `security` log line. The account is created in the same transaction as its mapping. `service_account_id` and `service_account_username` are returned on every mapping create, read, list, update and toggle, so the account can be granted access before any pipeline runs. New accounts are named `ci-<12 hex>`. If that name is already taken, mapping creation fails with a `409` that names the conflicting account; previously a pipeline would have hit the collision at run time. Deleting a mapping, or a provider with its mappings, now deactivates its account rather than leaving it active, and revokes its refresh tokens. The account row is kept so its audit history stays attributable. Deactivation now sticks: an exchange for a deactivated CI account is refused with `401`, where the federated sync previously set `is_active = true` again on every exchange, so the next pipeline silently undid an administrator's deactivation. Keying on the mapping also separates principals the old `sub` lookup merged: the same subject presented through two providers, or matched by two mappings, now authenticates as two accounts rather than one shared row. `docs/ci-oidc.md` is the first operator documentation for the feature. It covers setup, the one-mapping-one-principal model, granting access, the `.gitlab-ci.yml` shape, and the security boundary: a mapping whose any-of filter admits a fork trusts that fork exactly as much as the upstream.

  **Upgrade note — existing CI accounts keep their `users.id`, and with it their group memberships, permissions and audit history.** Migration 232 rewrites `external_id` in place on existing `auth_provider = 'ci'` rows. It resolves `ci-<8 hex>` to the one mapping whose UUID starts with those characters, and rewrites the row only when exactly one mapping matches. Rows whose mapping was deleted, and rows whose prefix two mappings share, are left untouched. The first exchange through their mapping adopts them when exactly one mapping carries the prefix, and refuses when several do. A unique 8-hex match is effectively, not provably, the original mapping: if that mapping was deleted and a later one happens to share its prefix (about 1 in 2^32 per pair), the row binds to the later mapping. Every decision, including later adoptions, is recorded with the previous key in `ci_oidc_service_account_rekey_log`, which is the migration's report and the input to the rollback statement in the migration header and in `docs/ci-oidc.md`. Existing `ci-<8 hex>` names are not renamed. Anything that parses a CI username as exactly 8 hex characters must accept 12 for mappings created from now on. **During a rolling upgrade, CI token exchange served by a replica still on the old version fails with the old 409 for any account that has already been re-keyed. Re-running the job after rollout completes succeeds.** In the same window, an old replica serving a mapping created by the new version does not find its `ci:`-keyed account and creates a stray `ci-<8 hex>` account keyed on the token subject. It has no grants and the new version never uses it; deactivate it after rollout. Mappings created before the upgrade report `service_account_id: null` until their account has been re-keyed or adopted.
