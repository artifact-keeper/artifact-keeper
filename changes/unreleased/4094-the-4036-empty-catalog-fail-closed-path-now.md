- **The #4036 empty-catalog fail-closed path now actually sees a zero-catalog scan, and no longer fires on artifacts that merely contain no libraries** (#4094). End-to-end verification on a live deployment with real conda-forge packages proved the original fix wrong on both sides. The miss: when grype catalogs *literally* nothing — any `.conda` package, verified against grype 0.118 — syft's cyclonedx-json presenter OMITS the `components` key entirely, and `parse_cyclonedx_catalog` returned `None` for a missing key, so the never-read case the fix was built for was still recorded `complete`; a valid grype-produced BOM without a `components` array now parses as `Some(vec![])` ("the engine ran and cataloged nothing"), with `None` kept strictly for unparseable BOM bytes. The false positive: `Some(vec![])` also fires when the BOM has components but no `type: "library"` ones — xz (`.tar.bz2`) cataloged 1 component with 2 real vulnerabilities, openssl (`.conda`) 1 component with 0 findings, and both were floored to F — so the hosted `not_cataloged` downgrade now additionally requires zero findings AND zero packages corroborating that nothing was read; an empty library catalog alongside real findings or a real inventory means "no libraries", not "never read", and keeps its scanner-reported completeness and grade. The knock-on is deliberate: the #3003 inline-proxy identity gate keys on `Some(cataloged)`, so a proxy scan where grype catalogs literally nothing now reaches the gate's empty-catalog inconclusive path (fail-closed 423) instead of skipping the gate as "no signal" — the gate's designed semantics finally firing. `parse_cyclonedx_packages` inventory semantics are unchanged: a missing `components` key there still means "no signal" and falls back to the match-derived rows.
