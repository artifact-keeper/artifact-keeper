- **Trivy scans no longer call Maven Central, and trivy and the dependency scanner grade the libraries bundled in a fat jar** ([#5666]). trivy's `pom.xml` parser resolved the parent POM and unpinned dependency versions of every POM in the scan workspace -- every extracted JAR carries one under `META-INF/maven/` -- against `repo.maven.apache.org`. On an air-gapped install that scan could not complete (a 429 from Central failed it on a connected one), it went around the Maven remote AK proxies, and it told Maven Central which dependencies the artifact uses; the version it recovered was the one a parent or BOM manages, not the one bundled. Every trivy scan (the scanner-adapter's image and filesystem scans and the backend's own `trivy filesystem` runs, including Incus rootfs scans) now passes `--offline-scan` and turns off trivy's per-run version check and telemetry call to `check.trivy.dev`. Separately, `trivy filesystem` never opens a JAR, so a Spring Boot fat jar was graded on nothing but its own POM; the backend now adds `.ak-scan-jar-inventory/pom.xml` to the workspace, naming each library bundled in any `.jar`/`.war`/`.ear` (`BOOT-INF/lib/`, `WEB-INF/lib/`, one level of nesting when the archive was not extracted) at the version its own `pom.properties` declares, so trivy grades them with no network access. The built-in dependency scanner (OSV) now unpacks JVM archives the same way: it queried a binary JAR for nothing and graded a fat jar bundling 141 libraries at 0 findings, and now queries each bundled library (`BOOT-INF/lib/`, `WEB-INF/lib/`, shaded `META-INF/maven/` entries) at its shipped version. Needs scanner-adapter 1.7.0 for the adapter-side flags; the inventory and the dependency-scanner change work with any adapter.
