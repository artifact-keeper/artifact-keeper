- **Stored environments and the component → environment reverse index: given a component or advisory purl, the registry now names the affected environments per platform, with the inclusion paths that pull the component in** (#4054). The incident question "what do we have to fix?" is asked against environments, not packages, but #4052's lockfile parser was a pure transformation and #4053's environment SBOM endpoint persisted nothing — so there was no stored fact to ask it against. This change adds the stored environment model: migration 226 creates `environments` (one row per `(repository_id, name)` — the repository is the unit of ACL and lifecycle, and re-ingesting the same name REPLACES the stored graph, since a re-solved environment is a new fact and stale membership would keep answering "are we exposed?" with an environment nobody runs anymore), `environment_packages` (one row per (scope, package) membership, carrying both the full #4041-qualified purl for display and its qualifier-stripped base), and `environment_edges` (one row per resolved edge, per scope). The reverse index is a btree on `environment_packages.purl_base`: the base is the identity an advisory carries (OSV/GHSA name a package and version range, not a conda build string), so a lookup reduces any qualified purl to its base and answers "which stored environments contain X" as an index scan — asserted by a DB test that seeds 300 environments and verifies the plan via EXPLAIN — while per-platform answers fall out of the scope columns every membership row carries. On a hit, the scope's stored rows are reloaded into a `LockedEnvironment` and the parser's own reverse-BFS (`LockedEnvironment::explain`) reconstructs the chains from a root down to the component, so the path answer is the same algorithm over the same data as the parse-time answer; paths are capped per hit (default 8, max 64) and hits per query at 500 (with a `truncated` flag). Served at `POST /api/v1/repositories/{key}/environments?filename=…&name=…` (ingest, repo `write`; 201 on first store, 200 on replace), `GET`/`DELETE` on the same nest for list/detail/delete, and `GET /api/v1/environments/lookup?purl=…&max_paths=…` for the reverse index across every repository the caller may read — visibility is rendered by the same `require_visible` predicate the repository listing uses, so a caller never learns that an environment in a repository they cannot read exists. Client telemetry (which users *ran* a component) is deliberately out of scope: this answers which stored environments contain it.
