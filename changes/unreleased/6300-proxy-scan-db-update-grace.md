- **A vulnerability-database update no longer re-scans every cached proxy package on its next pull** (#6300). A stored proxy scan verdict is reused only while its scanner version matches the live one, and that version includes the database build (`grype-0.120.1+db-2026-11-10`), so each daily update made every verdict stale at once: the next pull of every cached package scanned again on the request path (a `fail_closed` client waited for it or got a `423`) or queued a scan, all in the same hour. Now, for `PROXY_SCAN_DB_GRACE_HOURS` (default `6`, at most `72`) after the instance first sees a new build, a verdict the same scanner binary graded against the previous build still decides the pull, and that pull re-grades the cached bytes in the background against the new build: with the durable scan queue on, as a lowest-priority job within the workers' rescan slots; otherwise in the serving process, two at a time. A `vulnerable` verdict keeps blocking, nothing unscanned is served, and a scanner binary upgrade, a verdict two or more builds behind and an unknown version are re-scanned on the next pull as before. The window starts at the fleet's first sighting of the build, kept in the new `proxy_scan_db_versions` table (migration 401), so a restart or a new replica does not reopen it. A verdict graded against a newer build than the live one (during a rolling upgrade) is reused instead of being re-scanned with the older build. `ak_proxy_scan_regrades_total{outcome}` counts the re-grades. MEASUREMENT_PLACEHOLDER

  **Default change.** Within the window a pull can be decided by a verdict graded before an advisory the new build added. To keep the previous behaviour, where every database update re-scans on the next pull, set `PROXY_SCAN_DB_GRACE_HOURS=0`.
