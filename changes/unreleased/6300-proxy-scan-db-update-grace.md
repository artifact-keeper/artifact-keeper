- **A vulnerability-database update no longer re-scans every cached proxy package of a `fail_open` or `record_only` repository on its next pull; `fail_closed` repositories can opt in** (#6300). A stored proxy scan verdict is reused only while its scanner version matches the live one, and that version includes the database build (`grype-0.120.1+db-2026-11-10`). So each daily update made every verdict stale at once, and the next pull of every cached package scanned again, all in the same hour: on the request path under `fail_closed`, where the client waited for it or got a `423`, and as a queued scan under `fail_open`. Now, for a window after the instance first sees a new build, a verdict the same scanner binary graded against the previous build still decides the pull. That pull re-grades the cached bytes in the background against the new build: with the durable scan queue on, as a lowest-priority job within the workers' rescan slots; otherwise in the serving process, two at a time, with cached files waiting their turn.

  The window is `PROXY_SCAN_DB_GRACE_HOURS` for `fail_open` and `record_only` (default `6`, at most `72`) and `PROXY_SCAN_DB_GRACE_HOURS_FAIL_CLOSED` for `fail_closed` (default `0`, off; at most `24`). The re-grade is best effort; the window is the bound. A `vulnerable` verdict keeps blocking for the whole window, even when the new database would grade the bytes clean. Nothing unscanned is served. These are still re-scanned on the next pull as before: a scanner binary upgrade, a verdict older than the newest build recorded below the live one (chosen by build date, so a replica pinned to an old database cannot widen the grace), and an unknown version.

  The window starts at the fleet's first sighting of the build, measured on the database clock and kept in the new `proxy_scan_db_versions` table (migration 401). A restart or a new replica therefore does not reopen it. A digest whose re-grade is still queued when the window ends keeps the grace for at most one more window, so a backlog drains rather than falling back to scans on the request path all at once. A verdict graded against a newer build than the live one (one replica updated first, a rolling upgrade) is now always reused instead of being re-scanned with the older build. New metrics: `ak_proxy_scan_regrades_total{outcome}`, `ak_proxy_scan_regrade_backlog_oldest_seconds{where}` and `ak_proxy_scan_db_grace_window_seconds{action_class}`.

  Measured with `scripts/perf/proxy-scan-db-update.sh` over 200 cached Maven jars, after a simulated update: on a `fail_open` Remote at the defaults, none of the 200 pulls is served `pending` or queues a scan of its own (all 200 before). On a `fail_closed` Remote with the opt-in, 0 of 200 pulls wait for a scan (200 before) and p95 pull latency drops from 35.8 s to 0.05 s. The re-grades finish in the background within about five minutes. The env-parsing cases, the note on vulnerable verdicts and the performance note come from #6307 by @nicola-preda.

  **Default change.** `fail_open` and `record_only` repositories get the 6-hour grace by default; set `PROXY_SCAN_DB_GRACE_HOURS=0` to keep the previous behaviour. `fail_closed` repositories keep the previous behaviour unless the operator sets `PROXY_SCAN_DB_GRACE_HOURS_FAIL_CLOSED`. With that opt-in, a pull can be served clean from a verdict made before the new DB added an advisory, for at most the window. Without it, each update still re-scans every cached package of a `fail_closed` repository on its next pull, so plan scan capacity for that.
