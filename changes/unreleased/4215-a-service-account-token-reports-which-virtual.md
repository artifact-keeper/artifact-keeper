- **A service-account token now reports which virtual-repository members it cannot reach, and why** (#4215). A token can be configured so that it reads nothing through a virtual repository, in two independent ways, and both were silent: the token's repository scope may not cover the members (#4130), or the service account may hold no grant on them. Either way the symptom is an empty listing and a 404, with nothing to search for, and the two are fixed in different places. `GET /api/v1/service-accounts/{id}/tokens/{token_id}/scope-analysis` now names each unreachable member with a reason from a closed set — `out_of_token_scope` or `no_grant` — so a client groups on the code instead of parsing prose. The token listing carries `unreachable_member_count` per token, computed for the whole page in three queries rather than one per row, so a console can flag a token without a request fan-out. `POST /api/v1/service-accounts/repo-selector/preview` accepts an optional `service_account_id` and, when given one, returns the same `unreachable` set for a token that does not exist yet — which is where the mistake is actually made.

  The analysis deliberately lives in the backend: the rule it applies is `member_is_public || can_access_repo(member)`, so a **public member is exempt** and needs neither scope nor grant, and `GET /repositories/{key}/members` does not expose `is_public` — a client reconstructing this from the endpoints it has would be re-implementing an authorization predicate and would drift from it. Entitlement is judged before scope, because a member the account cannot read is not fixed by widening the token. An unrestricted token has nothing out of scope by definition but is still checked for missing grants, against the virtual repositories its owner holds a grant on. Asking without a `service_account_id` reports scope only, since whose grants apply is then unknown. Nothing is refused or blocked: a token may legitimately be scoped to a virtual whose members arrive later, so this informs and does not gate.
