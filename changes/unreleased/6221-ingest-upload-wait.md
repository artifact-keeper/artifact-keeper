section: Fixed

- **Five or more concurrent uploads to one repository now queue briefly instead of failing with 503** (#6221, #6191). An upload whose package metadata has to be read out of the archive needs one of a small number of decode slots (4 per repository, 8 in total), and when they were all taken it got `503 Too many concurrent uploads for this repository` at once. twine and poetry do not retry a failed upload POST, so a CI matrix publishing five or more wheels to one repository in parallel could fail against a healthy server. Such an upload now waits up to `INGEST_EXTRACTION_WAIT_SECS` (default 15, at most 30) for a slot before it is shed with the same 503 and `Retry-After` as before. The wait counts toward `GLOBAL_REQUEST_TIMEOUT_SECS` on the format upload routes. A PyPI upload's package analysis reuses the upload's slot rather than queueing a second time. The slot limits are unchanged, so concurrent decompression memory and CPU stay bounded, and the number of waiting uploads is capped as well (`MAX_QUEUED_INGEST_EXTRACTIONS_PER_TENANT`, default 8, at most 32, and `MAX_QUEUED_INGEST_EXTRACTIONS`, default 32, at most 128, so at most 112 uploads are parked with the defaults); past those an upload is shed at once. This applies to the upload paths that read the archive on a background thread: PyPI, NuGet, Helm, Dart pub, Swift, Ansible, pacman, MCP server and agent-plugin uploads, and npm and PyPI packages finalized through the chunked upload API. The other formats wait the same way (#6230). Set `INGEST_EXTRACTION_WAIT_SECS=0` to restore the immediate shed.
