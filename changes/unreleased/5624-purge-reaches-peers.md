- **Purging an artifact, deleting it with `?permanent=true`, or deleting its repository now removes it from push and mirror peers too** (#5624). `sync_tasks.artifact_id` cascaded on the artifact row (migration 008), so removing the row also removed the delete tasks queued for its peers, and the peers kept serving the artifact; with `?permanent=true` the delete was queued and then dropped within the same request. Migration 340 changes that foreign key to `ON DELETE SET NULL` and gives each delete task the repository key and path it removes on the peer (`target_repository_key`, `target_path`), so the task outlives the row and the sync worker sends `DELETE /api/v1/repositories/{key}/artifacts/{path}` from it. `DELETE /api/v1/admin/trash/{id}`, `?permanent=true` and each batch of a repository delete job queue those deletes for every push/mirror subscriber in the same transaction that removes the rows. A repository delete addresses them by the key the repository had before the job renamed it. A delete still queued when the path holds a live artifact again (re-uploaded or restored) is cancelled, and that artifact's push is held until an in-flight delete of the path finishes. The sync worker sweeps the push tasks of removed artifacts that the cascade used to delete.

  Migration 340 is catalog-only and short-lock. It adds four nullable columns without defaults, drops `NOT NULL` on `artifact_id`, re-adds the foreign key `NOT VALID` (no scan), and backfills only the unfinished delete tasks. Dropping a foreign key takes `ACCESS EXCLUSIVE` on `sync_tasks` and `artifacts`, held only for the catalog swap; each attempt waits at most 5s for its locks and retries up to five times.
