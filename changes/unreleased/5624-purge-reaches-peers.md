- **Purging an artifact, deleting it with `?permanent=true`, or deleting its repository now removes it from push and mirror peers too** (#5624). `sync_tasks.artifact_id` cascaded on the artifact row (migration 008), so removing the row also removed the delete tasks queued for its peers, and the peers kept serving the artifact; with `?permanent=true` the delete was queued and then dropped within the same request. Migration 340 changes that foreign key to `ON DELETE SET NULL` and gives each delete task the repository key and path it removes on the peer (`target_repository_key`, `target_path`), so the task outlives the row and the sync worker sends `DELETE /api/v1/repositories/{key}/artifacts/{path}` from it. `DELETE /api/v1/admin/trash/{id}`, `?permanent=true` and each batch of a repository delete job queue those deletes for every push/mirror subscriber in the same transaction that removes the rows; a repository delete addresses them by the key the repository had before the job renamed it. When the same key and path hold a live artifact again (re-uploaded, restored, or in a repository re-created under that key), the delete is cancelled only for a peer that artifact is pushed to, and the push waits for an in-flight delete of that path; a peer with a disabled subscription or a policy that excludes the new artifact still gets the delete. The sync worker sweeps the push tasks of removed artifacts that the cascade used to delete.

  Upgrade notes. **340** takes `ACCESS EXCLUSIVE` on `artifacts` and `sync_tasks` together, in the order the application uses, and holds both through the backfill of unfinished delete tasks (about 15 µs per row) and the catalog swap; nothing is rewritten or scanned for validation (the columns are nullable without defaults, the foreign key is re-added `NOT VALID`). Requests touching either table wait for that window. Each attempt waits at most 5 s for the locks; a lock timeout or a deadlock is retried, five attempts in about 35 s. If all fail, the server exits with nothing of 340 applied, and the next start retries it. **341** builds `idx_sync_tasks_artifact_id` with `CREATE INDEX CONCURRENTLY`, which blocks no reads or writes; without it every deleted artifact row scanned `sync_tasks` for its foreign-key action. Like 297, the build first waits for transactions already open on `sync_tasks`, so a long-running transaction delays the start; an interrupted build is dropped and retried at the next boot.
