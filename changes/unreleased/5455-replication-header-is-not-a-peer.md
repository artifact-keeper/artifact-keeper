- **A service account sending `x-artifact-keeper-replication: true` no longer gets peer-replication exemptions on the generic upload and delete routes** (#5455). The header is set by the client, and the chunked upload session, the raw and multipart generic `PUT`/`POST` and the generic artifact `DELETE` read "a service account plus the header" as a peer. Any CI account with `write` could therefore skip the storage quota, attach its own artifact metadata in place of the server-derived metadata, overwrite a replicated row in place, delete in-flight replication upload sessions for the same path, and soft-delete a released (immutable) artifact: an npm release's `DELETE` answered `200` instead of `409`. All of these paths, and the MCP refusal, now take the decision from one helper: the header counts only alongside an instance administrator's token, which is how a peer link is set up (`docs/mcp-registry.md`). A service account with the header is treated as an ordinary writer. **A peer link whose `api_key` is a service-account token on the receiving instance loses these exemptions**: re-issue it as an administrator's token. The chunked commit re-checks the decision for the principal completing the session, so a session opened by a peer and completed by anyone else cannot write to an MCP registry. A server.json that a peer replicates through the generic routes now writes the `MCP_SERVER_PUBLISHED` audit row, and the generic `DELETE` records its caller as the `ARTIFACT_DELETED` actor instead of a null actor.
