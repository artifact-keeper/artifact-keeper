- **Webhooks can be signed with an instance Ed25519 key and verified against a public JWKS** (#4401, first slice of #921). A webhook's new `signing_mode` (`hmac`, the default; `asymmetric`; or `both`, set at create time and returned by GET/LIST) decides which tokens `X-ArtifactKeeper-Signature` carries. `asymmetric` and `both` add `v2=<kid>:<sig>`, an Ed25519 signature (base64url, no padding) over `<t>.<webhook_id>.<body>`, and send the destination in `X-ArtifactKeeper-Webhook-Id`. Receivers no longer need a shared secret: they check that the webhook id is their own and verify the signature against `GET /api/v1/webhooks/jwks`, which needs no credentials and stays reachable when guest access is disabled. The webhook id is part of the signed message because one key signs for every webhook on the instance; without it, a delivery captured at one receiver would verify at another. The `kid` is the key's RFC 7638 thumbprint. The instance key is created on first use, and its private half is encrypted at rest with `AK_WEBHOOK_SECRET_KEY`, so `asymmetric`/`both` need that key set (create returns 422 without it). Existing webhooks stay `hmac`, and their headers are byte-identical to before. Receivers that only check `v1=` ignore `v2=`.

  If `AK_WEBHOOK_SECRET_KEY` is changed after the signing key exists, asymmetric deliveries go out without `v2=` and asymmetric creates return a 422 that says so. Until key rotation ships, an administrator recovers with `UPDATE webhook_signing_keys SET retired_at = NOW() WHERE retired_at IS NULL;`, after which a new key is created on next use. Key rotation with an overlap window and sample receivers will follow.
