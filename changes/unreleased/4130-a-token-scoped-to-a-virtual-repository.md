- **A token scoped to a virtual repository now says why it sees nothing, and can be minted to cover the members instead** (#4130). A virtual repository's listings and downloads both resolve its MEMBERS and drop the ones outside the presenting token's repository scope, and the parent being in scope says nothing about them. A read-only token scoped to the virtual therefore returned `200` with an empty page and 404'd every download, with no error, no log and nothing in the body to explain it — the repository looked empty, or the grants looked wrong. Adding write scope changed nothing, because the repository allowlist and not the action scopes is what drops the members; only `*` or naming the members worked. The scope rule itself is unchanged (#3081, #3163, #3174): a listing may not enumerate a member the token is scoped away from.

  Two things change. The `GET /api/v1/packages` and `GET /api/v1/repositories/{key}/artifacts` responses carry a `notices` array, which reports `members_out_of_token_scope` with the number of members omitted. The count includes only members the caller is ENTITLED to read and its own token excludes, so it describes the caller's credential against the caller's own grants and reveals no repository that `require_visible` would have hidden. And `repo_selector` gains `include_virtual_members`, which expands every matched virtual repository into its members; because a selector is re-resolved at authentication time, a member added to the virtual later is covered without re-minting the token. The flag widens a match rather than filtering, so a selector carrying nothing else still resolves to nothing — and since an empty selector means unrestricted, minting one is refused rather than silently issuing a token for every repository.

  The members are added for READS only. A token's repository scope is otherwise a ceiling for every action, and nothing can be published to a virtual repository at all (a write there answers 400), so write reach would serve no workflow while handing the token mutation rights over a member list maintained elsewhere — one that can grow after the token is minted. The decision is made once, where the credential becomes a principal: a read request gets the members in its scope, a write request never sees them, so every handler downstream refuses a write to an expanded member without having to know the rule exists. A request counts as a read if it uses a safe method, or is one of the POSTs a public repository serves to anonymous readers (the VS Code gallery query, PyPI XML-RPC); anything else is treated as a write, so a misjudged request fails as a refused read rather than a permitted write. A member the selector ALSO matches in its own right keeps full access. The expansion rides a JWT exchanged from the token as its own claim, applied the same way, so the OCI flow reads members through a virtual repository and still cannot push to them.

  One consequence of resolving at authentication time remains: a member REMOVED from the virtual stays readable until the validated-token cache entry expires (5 minutes) and for the lifetime of any JWT already exchanged from the token. Revoke the token to cut that short.
