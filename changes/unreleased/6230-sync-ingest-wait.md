---
section: Fixed
issues: [#6230, #6221]
---
- **RubyGems, conda, Debian, Hex, Composer, CocoaPods, VS Code extension, protobuf, Incus and Swift requests no longer fail with 503 while other uploads are queued** (#6230, #6221). These formats read the archive inline, and their archive read still took its slot with an immediate try: when no slot was free they got `503 Too many concurrent uploads for this repository` (or `Server is busy decompressing other uploads`) at once. Because a freed slot goes straight to an upload already waiting for one, during a burst of PyPI, NuGet, Helm or other waiting uploads they got the 503 every time, even though slots were turning over. They now wait for a slot the same way, up to `INGEST_EXTRACTION_WAIT_SECS`, with the same queue caps, and are shed with the same 503 and `Retry-After` only after the wait. This also covers the read paths that decode an archive (PyPI wheel and sdist metadata, Debian `Packages` index lookups, protobuf bundle downloads, the Swift manifest), and best-effort analysis that used to be silently skipped when no slot was free: conda metadata and install-script analysis (now read under the upload's own slot, before the package is stored), Debian maintainer-script analysis and Incus image metadata. The slot limits are unchanged, so concurrent decompression memory and CPU stay bounded. Set `INGEST_EXTRACTION_WAIT_SECS=0` to restore the immediate shed.
