- **Concurrent `npm publish` of the same `name@version` can no longer leave a losing request's tarball under the winning version, and the losers now get `409` instead of `500`** ([#5399]). Every publish of a version writes the same storage key, and the duplicate check ran without a lock before the write, so a request that lost the race could replace the winner's tarball after the winner's row had committed. The version's checksum and `dist.integrity` then named bytes that were not in storage: `npm install` failed with `EINTEGRITY` or the download was cut off, until the version was deleted. Most losers also got `500 DATABASE_ERROR`. A hosted npm publish now takes a per-version lock, checks again for an existing version while holding it and answers `409 Conflict` before it writes anything. It writes the tarball and commits the version row under that lock, and on a failed publish removes the object only when no committed version uses it. This is the npm counterpart of the Maven fix for #4892. Upgrading: to find versions damaged before this fix, run the storage scrub (`POST /api/v1/admin/storage-scrub`, see `docs/operations/download-integrity.md`), then delete and republish any version it reports.
