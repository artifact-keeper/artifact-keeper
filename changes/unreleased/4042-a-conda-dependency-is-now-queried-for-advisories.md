section: Added
issues: [#4042, #4088, #4089]

- **A conda dependency is now queried for advisories as the PyPI distribution it corresponds to, and a conda package the registry cannot identify degrades the scan instead of reporting it clean** (#4042, #4088, #4089). OSV has no `conda` ecosystem and the GitHub Advisory Database does not index one — `query_github_detailed` mapped ecosystems with a `match` whose `_` arm was `continue` — so a conda dependency got **nothing** from either feed and the result was bit-for-bit indistinguishable from a clean scan. The dependency scanner now resolves each conda name through the alias graph in `conda_identity` and branches on all three coverage states, which are three different facts and are never collapsed into one: a **mapped** name is queried as that PyPI distribution (OSV `PyPI`, GitHub `pip`), which is real coverage; a name that positively ships no PyPI distribution is queried **unscoped**, exactly as a vendored native library is, which is real but weaker; and a name that *is* a Python package whose alias the registry does not know becomes a coverage gap that **degrades the scan to `partial`** rather than letting an unidentifiable package render as clean. A finding names the package the reader actually installed (`py-opencv`), with the alias it was looked up under (`opencv-python`) disclosed in the description, so nobody is sent to patch a package they never installed. `AdvisoryLookup` gains `not_queried`, deliberately distinct from `degraded`: an ecosystem GitHub does not index was never asked about, which is not the same as a feed that was asked and failed — and both differ again from asked-and-clean. Shipped with it, `analysis_degraded` is now genuinely covered in the `feeds_degraded` disjunction (#4088): the term could be deleted and the entire suite still passed, because the test that appeared to exercise it used a fixture with no declared dependencies and returned before ever reaching it.

  **Honest limit — an alias-mapped query sends the conda version string to PyPI advisory ranges verbatim.** There is no conda→PEP 440 conversion and no local comparison: the version is copied straight from the conda coordinate into a `PyPI`-ecosystem query and all range evaluation happens server-side at the feed. Where the two version lines diverge, the answer can be wrong in the over-reporting direction — conda-forge's `py-opencv 4.9.0` against PyPI `opencv-python 4.9.0.80`, a backend-scoped CVE reported against the GUI-less `matplotlib-base`, or a conda rebuild that patches a vendored library and bumps only the build string. Every such finding's description carries that caveat, but the false-positive rate is not measured and no test bounds it; read an alias-mapped conda finding as "the PyPI distribution this package corresponds to has this advisory", not as a confirmed match against the bytes on disk.
