- **An OIDC or SAML sign-in, and the exchange code it produces, can only be completed by the browser that started it** ([#5486]). The OIDC `state`, the SAML AuthnRequest id and the single-use exchange code were not tied to the browser that started the sign-in, so another browser could complete it and end up signed in to someone else's account (login CSRF). The OIDC and SAML login redirects now set a per-sign-in `ak_sso_bind_*` cookie (`HttpOnly`, `SameSite=Lax`, `Path=/api/v1/auth/sso`, 10 minutes) whose value is an HMAC of the state under `JWT_SECRET`. The OIDC callback requires it before the state is consumed, and every exchange code carries a MAC over it, so `POST /api/v1/auth/sso/exchange` redeems a code only with that cookie and then clears it. The SAML ACS is a cross-site POST that carries no such cookie, so it no longer sets a session on its response. It answers `303 See Other` to the new same-site step `GET /api/v1/auth/sso/complete?code=…`, which checks the cookie, sets the session cookies and redirects to the web UI's `/callback` as before. A refusal is `401 AUTH_ERROR` and consumes nothing. A refused OIDC callback is audited as `LOGIN_FAILED` with `details.reason = "sso_browser_binding"`. A command-line client starts its sign-in with `client=cli` on the login URL and keeps the cookie itself. Its callback then sets no session in the browser and shows the exchange code, which only the client can redeem. An `ak` CLI without that support can no longer finish OIDC or SAML browser sign-in. LDAP, API tokens and the device flow are unaffected. During a rolling upgrade from 1.11.x, a sign-in started on an old replica and finished on a new one is refused and has to be started again. See `docs/sso-login-binding.md`.
