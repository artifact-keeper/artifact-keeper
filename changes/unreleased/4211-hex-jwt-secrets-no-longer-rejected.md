section: Fixed
issues: [#4211]

- **A hex `JWT_SECRET` is no longer rejected as low entropy just because it happens to miss one of the sixteen hex digits** (#4211). Since 1.7.0 the startup check has refused any secret with fewer than 16 distinct characters, in every environment. A hex secret can contain at most 16, and a random 64-character one (`openssl rand -hex 32`, 256 bits) misses at least one digit about 23% of the time, so roughly one deployment in four with a freshly generated hex secret refused to start with `JWT_SECRET is unsuitable: it has low entropy`. The distinct-character count is replaced by an entropy estimate from the character classes the secret uses (4 bits per character for hex, 6 for base64 or base64url, up to log2(95) for printable ASCII), and a secret must reach 128 estimated bits, so 32 hex characters is the minimum hex secret. A string drawn from only a few symbols is still judged by the symbols it actually uses, so 40 characters from five letters remain rejected. The 32-character minimum, the placeholder and weak-substring lists, and the monotonic-sequence check are unchanged, and a short unit repeated (`abab…`, `0123456789abcdef` four times) is now rejected even when it has 16 distinct characters. The error still recommends `openssl rand -base64 48` and now says a 64-character hex secret is accepted too.
