- **A proxy rescan no longer weakens the `vulnerable` verdict of a `.deb`, `.rpm` or `.apk` graded against its release, or of a Go, Composer or Conan archive graded as its coordinate** ([#5628]). `POST /api/v1/repositories/{key}/security/proxy-scans/rescan` has no request to name the release an OS package is graded against (`rhel:9`, `debian:12`) or the coordinate an archive is graded as. Without a release, the engine catalogs a `.rpm` or `.deb` from its own header and finds nothing. That scan cataloged as many components as the stored verdict, so the 1.12.0 "fewer components" rule let it record `clean`. The rescan response, `/security/proxy-blocked` and the dashboards then showed a vulnerable package as clean until its next pull re-graded it (downloads stayed refused). A rescan that found the package vulnerable at a lower severity was recorded too, and dropped the stored pin. Now, when the stored `vulnerable` verdict was graded as such a coordinate, a rescan replaces it only when it finds the package at least as severe, and the stored pin is kept. Any other result answers 503 `RESCAN_REQUEST_PINNED`, with no `Retry-After` since a retry cannot succeed, and leaves the verdict, pin and findings unchanged. Pull the package through the proxy to re-grade it.
