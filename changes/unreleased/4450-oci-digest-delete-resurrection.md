- **An OCI image deleted by digest no longer comes back after a restart** (#4450). `DELETE /v2/<name>/manifests/<digest>` removed every tag and index row for the digest but soft-deleted only the `artifacts` row at the digest path, so the tag's own row (`v2/<image>/manifests/<tag>`) stayed live. On the next start, the OCI migration reindex took that row for a never-indexed migrated manifest and re-registered the tag, its child refs and its `oci_manifests` record: an image an operator had deleted, for example a compromised one, was pullable again after any restart or rollout. A delete by digest now soft-deletes every manifest row of that image name whose bytes are that digest (other image names in the repository keep theirs, #4466), tag rows included, in the same transaction as the index unwind (a failure rolls both back; the soft-delete error used to be dropped). The startup reindex also skips a live manifest row when the same manifest was deleted by digest after that row was last written, so a row left behind by an older replica during a rolling upgrade is not revived either, when the image was also pushed by digest. Deleting by tag name is unchanged, and a child manifest still listed by another tagged index stays. An image pushed only by tag and deleted by digest before the upgrade, or by a not-yet-upgraded replica during the rollout, leaves nothing to tell it apart from a migrated manifest, so a restart (including the upgrade itself) may still revive it: check images deleted by digest before and during the rollout and delete them again once every replica runs this release (#4465 tracks closing that gap).
