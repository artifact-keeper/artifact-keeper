- **A proxied conda repodata response is now attributable to a recorded upstream repodata patch generation** (#4051). Upstream conda channels rewrite the dependency metadata of ALREADY-published packages via repodata patching: the artifact hash never changes, but resolution behavior does, so two solves months apart against the same channel and the same package hashes can produce different environments with no recorded difference to point at. When a Remote conda repository serves an index (`repodata.json` / `.bz2` / `.zst`), the registry now also fetches the upstream `{subdir}/patch_instructions.json` through the same proxy cache, content-addresses it — the generation is the BLAKE2b-256 hex of the served bytes, which works across upstreams that do not version their patch documents — records it in the new `conda_repodata_patch_generations` table (migration 225, one insert-only row per distinct generation per repository/subdir), and names it on the response in the `X-Repodata-Patch-Generation` header. A header rather than an extra top-level key: repodata.json is parsed by conda clients against the CEP schema, and a header cannot perturb the document a client solves against at all — the body is still served byte-identical to upstream, and no dependency metadata is rewritten. Identical upstream patch content maps to the same generation (`ON CONFLICT DO NOTHING`, so the hot serve path never becomes a per-request UPDATE), while an upstream patch revision appears as a NEW row with a later `first_seen_at` — a change that is visible as a change, not silent. Recording is best-effort by design: an upstream that serves no patch instructions (404), a transient upstream failure, or a recording failure never takes down the repodata serve — the response simply carries no attribution header. Hosted (local) and virtual channels are untouched: there is no upstream patch authority behind them, so there is nothing to attribute, no header, and no rows.
