- **Remote repositories can restrict which paths they request from their upstream, and a virtual repository no longer waits on a member whose filter excludes the path** (#4399, #840). A new per-remote upstream filter (`GET`/`PUT`/`DELETE /api/v1/repositories/{key}/upstream-filter`, repository admin only) takes `include_patterns` and `exclude_patterns` regexes, the same shape as a peer's `replication_filter`, matched against the path as sent upstream (anchor with `^`/`$`): for Maven, Debian, OCI and Go the layout path such as `com/acme/lib/1.0/lib-1.0.jar`; for npm the encoded `@scope%2Fname` for metadata and `@scope/name/-/...` for tarballs; for downloads from another host (PyPI files, cargo `dl` hosts, NuGet service URLs) the full URL. A path the filter refuses answers 404 without contacting the upstream, so a virtual repository skips that member for it: a fringe Maven remote that hosts a handful of groups can be limited to them, and when it goes down it no longer stalls every `maven-metadata.xml` merge until the upstream timeout. Patterns are validated on write (at most 64 per list, 512 bytes each, each list compiled to at most 64 KiB; subjects over 4 KiB are refused), and a change applies on every replica at once. The npm `/-/` passthroughs and npm audit, curation upstream sync, change feeds and the `test-upstream` probe are not filtered yet. An object already in the proxy cache for a now-filtered path is served until its cache entry expires; it is then refused with 404 like any other miss (no revalidation, no stale-if-error), and the cache invalidate endpoint removes it immediately. This is the first slice of the remote-repository policy work; package-name, size and vulnerability rules are not part of it.
