- **A VS Code extension publish now reads the uploaded `.vsix` instead of trusting three request headers** (#3961). `POST /vscode/{repo}/api/extensions` took the publisher, name and version from `x-publisher` / `x-extension-name` / `x-extension-version`, never opened the archive, and stored four fields. Nothing editor-visible was recorded, which is why the catalog row from #3659 had no description, and why a gallery response cannot be built from a published extension: a client needs `engines.vscode` to decide whether it can run one, and `targetPlatform` to choose between platform-specific builds. Both manifests are now parsed into the existing `artifact_metadata.metadata` JSONB (no migration): `extension/package.json` for `displayName`, `description`, `engines.vscode`, `icon`, `categories`, `extensionDependencies` and `extensionPack`, and `extension.vsixmanifest` for `Identity/@TargetPlatform` and the pre-release property, which `package.json` does not carry. Extraction runs under `bounded_archive::with_ingest_extraction` on the shared ingest budget, and a corrupt archive, a missing manifest or a missing `engines.vscode` is a 400.

  **Upgrade note — a publish that works today keeps working.** `vsce package` output publishes with no headers at all. Headers that are sent are checked against the archive — identity casefolded, version exact — and a disagreement is refused with a 400 naming the header instead of one side being picked silently. A body that is not a VSIX at all (not a zip, or a zip with no `extension/package.json`) still publishes on the header coordinates and produces the same four-key record as before, with a log line saying so; a VSIX whose manifest is present but invalid is a 400 even when all three headers are sent, so a broken manifest cannot route around the header check. Those coordinates are now validated before they become an artifact path and a storage key; they previously reached both with no charset check.
