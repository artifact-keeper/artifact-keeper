- **Upload scans and pushed OCI images run from the durable scan queue** (#5946). With `SCAN_QUEUE_ENABLED=true`, proxy file scans and `POST /api/v1/security/scan` already ran as queue jobs, but `scan_on_upload` still spawned its scan in the process that took the upload, so the heaviest scans (container images, through the scanner adapter and grype) ran on the pods that serve requests and were lost on a restart. With the queue on, a `scan_on_upload` now queues a job at the hosted priority instead: a pushed OCI manifest is one `hosted_image` job per repository and manifest digest, so pushing the same manifest again, or under another tag, while the job is pending adds no second one, and every other format is one `hosted_upload` job per artifact. A push or upload that arrives while its job is running marks the job to run once more. The worker scans exactly as the in-process trigger did (migration 383). `SCAN_WORKER_TRIVY_ADAPTER_URL` gives the worker's scans their own scanner-adapter URL, so a worker pod can use an adapter next to it while API pods keep `TRIVY_ADAPTER_URL`. If a job cannot be queued, the scan runs in-process as before. With the queue off, nothing changes.
