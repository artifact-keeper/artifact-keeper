---
section: Fixed
issues: [#4147, #4160, #4058]
---
- **The conda channel allowlist now actually fails closed on an unknown channel of origin** (#4147, #4160, #4058). `load_conda_facts` resolved the artifact's channel from its identity purl and then chained `.or(Some(row.repo_key))`, so a conda artifact whose identity declares no channel — a pre-identity upload, or a purl carrying no `channel` qualifier — was attributed to the **key of the repository it happens to be stored in** rather than to "unknown". Operators allowlist their own repository keys as a matter of course, so such an artifact silently **passed** an allowlist it should have been blocked by, and the `[conda.channel]` "channel of origin is unknown" branch the code comment, the PR body and this changelog all advertised was unreachable in production — exercised only by hand-built fact structs in unit tests. That allowlist is #4058's main defence against channel-priority misconfiguration and typosquatted channels, so the one predicate documented as fail-closed was the one that failed open. The fallback is removed: an absent channel is `None` and takes the deny branch.

  **The same issue turned out to be wider than the fallback.** Verified against a live deployment: a policy scoped to the source repository carrying `predicates.conda.allowed_channels` promoted its artifact with `policy_violations: []`, and so did `denied_channels`, `denied_licenses` and `origin.allowed_kinds` — while the same policy's `max_severity` blocked correctly, proving the gate itself ran. The cause is that promotion is evaluated by `PromotionPolicyService`, a second gate that reads the same `scan_policies` rows for `max_severity`, `block_unscanned`, the age gates and `require_signature` but never read `predicates` at all — so **the entire predicate block, conda and origin, was inert on the enforced promotion path**, and a channel allowlist that blocked a download waved the same artifact through the operation that raises its trust level. Both gates now evaluate the predicates through one shared entry point, `PolicyService::evaluate_predicates`, so they cannot disagree again; a predicate violation is reported on the promotion response as a `policy-predicate` rule at `high` severity, which blocks, and carries the same `[conda.channel]` / `[origin.kind]` token the download gate records. Predicates are evaluated across every applicable policy (repository-scoped and global), matching the download gate, where promotion's own severity gate takes only the single most specific policy — deliberate, and in the fail-closed direction.

  Five DB-backed tests pin all of it: an artifact with no declared channel is denied by an allowlist that contains its own repository key; a hosted artifact is evaluated on the channel its identity declares rather than on the repository key; and three drive `PromotionPolicyService::evaluate_artifact` — the exact call the promote handler makes with `skip_policy_check: false` — for the allowlist, the denylist and the predicate-free control. **Operator note:** a policy using `allowed_channels` will now block conda artifacts that carry no channel in their identity purl, where before it let them through; that is the intended behaviour, and anything that must be served needs a channel recorded at ingest or an explicit allowlist entry it genuinely matches.
