- **An MCP introspection result is refused when its server version stopped being eligible after the claim** (#5463). A completion used to re-check only the claim token and the worker's repository scope, so a result for a version quarantined, rejected, marked deleted or deleted after the claim, or whose backing package was quarantined or deleted, was still stored and could become the version's current capability view. A completion now evaluates the reader serve gate a claim passes once more before its transaction, and inside the transaction that ends the claim re-reads, under lock, the version row's quarantine, rejection and deletion, its registry status (`deleted`), and every backing package's pinned rows (quarantined, rejected, deleted, or a cache pin under its hold), so a concurrent quarantine or deletion of those rows waits for the commit. A target that no longer qualifies answers `409 mcp_target_ineligible`, stores nothing and cancels the job, as a claim of a held version already did; a worker whose repository scope no longer covers the job still gets `403 mcp_forbidden`. The remaining gates (scan policy, curation and age gates, Remote proxy verdicts, OCI manifest presence) are evaluated only by that pre-transaction check; #5533 tracks evaluating the whole gate on the transaction. A gate that cannot be evaluated is no longer treated as a hold, at claim or at completion: the claim answers `503 mcp_gate_unavailable` and returns the job to the queue without spending its attempt, and a completion answers `503 mcp_gate_unavailable` and leaves the claim as it was, so a transient database error no longer cancels a job (and with it the remote's re-probe schedule). This concerns the capability state repository holders see; it does not change what is served to package clients.
