- **Project admins can manage their own project's membership and create repositories in it** (#2473). A principal holding `admin` in a project grant (`POST /api/v1/projects/{id}/members` with `actions: ["admin","read","write","delete"]`, directly, as a service account, or through a group) may now `GET`/`PUT /api/v1/projects/{id}` and list, add and remove that project's members, which previously required a global admin. Listing, creating and deleting projects, changing a project's `quota_bytes`, and the global `/api/v1/permissions` API stay global-admin-only, and a credential restricted to a repository allowlist is never treated as a project admin. `POST /api/v1/repositories` now accepts a project admin when the request assigns the repository to that same project; repository data-plane access for the project's admins comes from project inheritance, with no per-repository grants written. Because permission actions match exactly, the role needs all four actions: `admin` alone gates management but grants no read or write.

  Repository keys may follow the optional `<project.key>-<name>` convention. A repository assigned to a project whose key starts with another project's `<key>-` prefix is rejected with 400 on create and on a rename or reassignment, so a project admin cannot mint names in another project's namespace; keys that use no project's prefix are unaffected, and keys and URLs stay flat. Reassigning a repository to a different project through `PATCH /api/v1/repositories/{key}` now requires a global admin, a system-level repository admin, or project admin on the destination project; repository admin alone is no longer enough.
