- **Completing a chunked upload onto an occupied immutable path is now refused with 409, instead of silently replacing the artifact** (#3924). `PUT /api/v1/repositories/{key}/artifacts/{path}` has always answered `409 CONFLICT` ("Artifact version already exists and is immutable") for a write to a taken coordinate, but `PUT /api/v1/uploads/{id}/complete` answered `200 OK` and overwrote the stored content — so the same logical write was rejected or accepted purely according to which upload API the client happened to use, and a chunked client could destroy a released artifact without ever seeing an error. `ArtifactService::preflight_upload` documents itself as "the single chokepoint every service-backed upload path flows through" and carries both immutability rules; the chunked completion handler was simply never on it, and committed the artifact through a bare `INSERT ... ON CONFLICT (repository_id, path) DO UPDATE` that unconditionally replaced `checksum_sha256` and `storage_key`. Both rules — the live-overwrite check and the tombstone-aware release-immutability backstop, which together are what stop a soft-delete followed by different bytes at the same released coordinate — now live in one shared `enforce_path_immutability`, called by `preflight_upload` and by the completion handler, so the two paths cannot drift apart again. The gate runs before the storage copy, so a rejected completion writes no bytes, and it *releases* the commit lease rather than failing the session: a 409 here becomes a legal write the moment the occupying artifact is deleted, so the client retries the session instead of re-uploading every chunk. It is applied unconditionally, matching the direct-write paths, which exempt replication from quota admission but never from immutability — a replica pushing identical bytes passes on the checksum comparison anyway, so what gets refused is a replication that would change the bytes under a released coordinate.
