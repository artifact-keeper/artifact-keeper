- **`terraform init` and `tofu init` install hosted Terraform modules** (closes #4590). A module's `.../download` answered `204` with an `X-Terraform-Get` location that named no archive type, so the client's getter fetched it as an HTML page looking for a `terraform-get` meta tag and failed on the archive bytes (`XML syntax error ... illegal character code U+0003`). The archive type is now detected from the bytes at upload (ZIP or gzip-compressed tar), recorded in the module's metadata, and advertised as `.../archive?archive=zip` or `?archive=tar.gz`. The archive is served with the matching filename and `Content-Type` instead of always `.tar.gz`. Modules uploaded before this release carry no recorded type, so theirs is read from the stored bytes on download, and they install without being uploaded again.

  An upload that is not a ZIP or a gzip-compressed tar is refused with `400` and the reason. That includes an uncompressed tar, which neither client can install (their module getter has no plain-tar support). Remote Terraform repositories now answer `.../download` with the same `204` + `X-Terraform-Get` pointing at their own `/archive`, which streams the upstream archive through the proxy cache. The hint comes from the upstream location's `archive=` parameter or extension, or from the bytes. Before, the upstream `204` body was relayed as an empty `200` without its header, which no client can use. A source the proxy does not fetch (a `git::` or `s3::` address, or an archive type other than ZIP and tar.gz) is passed to the client unchanged. A new native test, `scripts/native-tests/test-terraform-modules.sh` (e2e profile `terraform-modules`), runs the real CLI against a hosted ZIP module and a hosted tar.gz module through a host-level discovery rewrite.
