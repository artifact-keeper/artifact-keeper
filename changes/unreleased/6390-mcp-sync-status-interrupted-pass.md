- **`GET .../mcp/sync` reports a Remote MCP sync pass that ended without recording its outcome as finished, and a scheduled pass that fails on a database error records the failure** (#6390). A pass killed by a panic, a cancellation or the loss of its pod releases the repository's sync lock when its database connection drops, but it recorded nothing. Polls then answered `running: false` together with the previous pass's `lastFinishedAt` and `lastError`, so a client waiting for the pass could not tell that it had ended. Now the first poll that finds the lock free and a start with no later finish records the pass as ended: `lastFinishedAt` is set and `lastError` reads `the sync pass ended without recording an outcome: its sync lock was released while it ran (...)`. The write is a single conditional update. It is skipped while any replica holds the lock or once a newer pass has started, so it never overwrites a pass in progress. A pass checks every 5 s that it still holds its lock. One that has lost it (its lock session ended while the process lives on) stops and records `the sync pass lost its repository sync lock ...`. Every state write of a pass now matches its own `last_started_at`, so a pass that lost its lock can no longer overwrite the outcome, `updatedSince` or resume cursor of a pass that started after it. The scheduled pass (`sync_repo`) now also records a database error before it releases the lock, as the manual trigger does since #6249. There is no setting for this.
