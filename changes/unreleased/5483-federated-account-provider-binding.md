section: Security
issues: [#5483]

- **A federated account is bound to the identity provider that created it, so the same subject at a second provider no longer signs in as the first provider's user** ([#5483]). Sign-in matched an existing account by `(auth_provider, external_id)` alone. With two OIDC, SAML or LDAP providers configured, a user of provider B whose `sub`, NameID or DN equalled one of provider A's users (two GitLab instances both numbering users from 1, the default `emailAddress` NameID, a compromised partner IdP) was signed in as A's user: the sync overwrote that account's username and email, kept its `is_admin`, reactivated it and issued it tokens. Migration 350 adds `users.auth_provider_id` (the `oidc_configs` / `saml_configs` / `ldap_configs` id) and sign-in now matches on the provider as well, so B's user gets an account of its own. On upgrade an existing account is bound where its provider is certain: LDAP accounts to the provider they last signed in through, and every account of a type that has exactly one configured provider to that provider. Any other existing account (several providers of its type, nothing recorded) is refused at sign-in with `403 FORBIDDEN` and a `LOGIN_FAILED` audit event whose `details.reason` is `federated_account_unlinked`, until an administrator binds it to its provider; no second account is created beside it. CI service accounts are unchanged. See `docs/sso-account-binding.md`.
