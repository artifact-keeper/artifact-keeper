- **A releases repository took a SNAPSHOT deploy and a snapshots repository took a release: Maven and Gradle hosted repositories now have a version policy** (#5872). A misrouted deploy made a releases repository mutable for that coordinate or put a release under snapshot cleanup. `version_policy` (`mixed`, `release` or `snapshot`) is set on create and update of a local or staging Maven or Gradle repository, returned on its GET and on the repository listing, and carried by the admin config export and import. Under `release` a path in a `-SNAPSHOT` version directory is refused with 400 `Repository '<key>' accepts release versions only`, under `snapshot` a release version is refused the same way, artifacts, POMs, checksums and version-level metadata alike. On the Maven deploy route the reason is the HTTP status line too, which is what `mvn deploy` prints. Group and artifact level `maven-metadata.xml` is accepted under every policy. The policy holds on the Maven deploy route, the generic artifact upload, chunked upload sessions, checked again at commit (so peer replication too, below and above its chunked threshold), promotion, approval and the migration import. Setting a policy other than `mixed` on a Remote, a Virtual or another format is a 400 that leaves the rest of the update unwritten. Upgrade note: migration 423 adds the column with `mixed` for every existing repository, so nothing changes until a policy is set. Only the version directory decides, case-sensitive `-SNAPSHOT` like the Maven handler, so an artifact named `db-snapshot` is not a snapshot. A peer refusing a version for its policy fails that item, not the peer. Not covered: what a repository already holds is not re-checked when its policy changes, a trash restore is not checked, `sbt` repositories have no policy, and paths shorter than `group/artifact/version/file` pass. The Nexus and Artifactory importer mapping and the web form field continue in #6350. Contributed by @nicola-preda.
