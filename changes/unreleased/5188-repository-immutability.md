- **A repository can be made mutable so a re-upload replaces the existing file instead of answering 409** (#5188). Set the new per-repository `immutability` mode to `mutable` on `POST /api/v1/repositories` or `PATCH /api/v1/repositories/{key}` (it is echoed back on every repository response, carried by config export / import, and a change is recorded as `immutability_change` in the `REPOSITORY_UPDATED` audit details). Snapshot and development channels can then republish under the same version and filename ("latest build wins"), which clients with no overwrite option, such as `twine`, need. The default is `write_once`, so every existing repository keeps answering 409. The setting is a mode rather than a boolean so per-path rules (#4812) can extend it later.

  A replacement with different bytes is a new artifact: the old row is removed inside the publish transaction and the new bytes get a new artifact id, so the scan results, findings, promotion approvals and quarantine state recorded for the old bytes go with it and the new id is scanned on upload like any first upload. Re-uploading identical bytes is not a replacement and keeps the id (on the RPM, Alpine and Pacman routes it answers the same 409 as a write-once repository). A replacement that fails (quota, storage, the insert) leaves the old artifact exactly as it was, and the old object is handed to storage GC, which deletes it once nothing else references it. Per-artifact records that are not about the bytes (properties, labels, download counts) do not carry over either. Every replacement of a live file records an `ARTIFACT_OVERWRITTEN` audit event in the same transaction (streamed to the audit export only once it commits), carrying the retired artifact id, the old and new SHA-256, the uploader and the old artifact's scan verdict, so the trail keeps what the removed row no longer can.

  On PyPI only development (`.devN`) and local (`+local`) versions can be replaced; final releases and pre-releases stay write-once on a mutable repository until per-path rules (#4812) land. The mode is honoured by the direct, streaming and chunked upload paths, by the PyPI upload route, and by the system-package file-drop formats Debian, RPM, Alpine and Pacman. On a Generic repository with `versioning_enabled`, versioning still applies and a re-upload appends a revision instead. `mutable` is accepted only on local or staging PyPI, Debian, RPM, Alpine, Pacman and Generic repositories: `mutable` on any other format (npm, Cargo, Go, Maven, Helm and the rest, whose consumers pin published coordinates) or on a remote or virtual repository is refused with 422, and those repositories stay write-once on every upload route, the generic `PUT /api/v1/repositories/{key}/artifacts/{path}` included. OCI tags remain mutable through their own path. A mutable repository serves its package files, directly and through a virtual repository, with `Cache-Control: no-cache` and their SHA-256 as `ETag`. A remote repository whose upstream answers `no-cache`, `no-store` or `max-age=0` together with an `ETag` now revalidates that file on every read, even where it would otherwise cache it forever, so a remote in front of a mutable repository serves the replacement; the entry keeps its usual expiry, so serving it while the upstream is down works as before. A virtual repository reads its local members directly and already serves the replacement. Clients that pin hashes (`pip --require-hashes`, `poetry.lock`, `uv.lock`) will still reject a replaced file, so reserve `mutable` for channels whose consumers expect content at a path to change.
