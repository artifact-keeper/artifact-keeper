- **Warm a conda Remote's proxy cache from an ingested lockfile before a fleet run** (#4184, part of #4172). `POST /api/v1/conda/{repo}/warm` with a stored environment's id (`POST /api/v1/repositories/{key}/environments`) and an optional `platform` fetches every package file the lock pins into the cache of `{repo}` when it is a Remote, or of the Virtual's Remote members. A fleet installing that environment is then served from the cache, not the upstream. `GET /api/v1/conda/{repo}/warm/{id}` reports progress per item state (`fetched`, `cached`, `held`, `blocked`, `checksum_mismatch`, `failed`, `not_remote`, `not_allowed`), and `DELETE` cancels. The `ak_conda_warm_items_total{outcome}`, `ak_conda_warm_upstream_fetches_total`, `ak_conda_warm_bytes_total` and `ak_conda_warm_jobs_running` metrics track the same counts.

  Each package is fetched through the same Remote fetch path a client download takes, so the Package Age Policy hold, the origin policy and scan-on-proxy apply as they do on a cold miss. A warm fills the cache and serves nothing, and every later serve of a warmed entry passes the usual cache-hit gates. A package inside its hold is recorded `held` and is still refused (409) when a client asks for it. Asking again while a job runs returns that job. A package whose fresh cache entry already records the lock's sha256 is not fetched again. A file whose bytes differ from the lock's sha256 is reported `checksum_mismatch`, and the bytes the warm fetched are removed from the cache again. A warm of a Virtual scans under the Virtual's scan-on-proxy policy (the stricter of the Virtual's and the member's), as a download through it does. Jobs and items are stored (migration 425), so a restarted process resumes them. It needs repository `write` (or admin) on `{repo}`, read on each Remote member of a Virtual, and read on the environment.

  Bounded by `CONDA_WARM_CONCURRENCY` (default 8 fetches in flight per process) and `CONDA_WARM_UPSTREAM_RPS` (default 20 upstream fetches started per second per process), so warming does not compete with foreground serving. `CONDA_WARM_MAX_ITEMS` (default 50,000) caps one job. `CONDA_WARM_ITEM_LEASE_SECS` (default 600) is how long a claimed item waits before a restarted runner takes it over. `CONDA_WARM_ITEM_TIMEOUT_SECS` (default 300) bounds one package from first byte to cache commit, so a slow upstream cannot hold a fetch slot. `CONDA_WARM_MAX_JOB_BYTES` (default 100 GiB) caps the bytes one job fetches; the job then ends as `budget_exceeded`. A runner that keeps failing on database errors ends its job as `failed`. Lockfiles ingested from this release on record each package's URL and sha256. Environments ingested earlier report their packages as `skippedNoUrl` until they are ingested again.

  Measured with the `conda-warm-from-lockfile` tier (artifact-keeper-test): 8 parallel installers of a 1,000-package lock against a cold Remote sent at least 1,000 package requests upstream. After warming, the same fleet through a Virtual sent 0, and every body matched the lock's sha256.
