- **A CI OIDC identity mapping can now grant its service account access directly, instead of that access living in a second, disconnected group membership.** (#4117). `allowed_repo_ids` reads like a grant in HCL but was only ever a ceiling, intersected with the account's RBAC — and a CI service account was provisioned with no RBAC of its own, so the mapping alone authenticated a pipeline but never authorized it. Making a pipeline work took an unrelated second act in a different file: create a group, grant it repository actions, add the service account to it by hand — three commits per pipeline on this project's own `test` instance. A mapping now accepts `group_binding_ids`, the set of groups its service account SHALL belong to; declare it and the account has exactly that access from the moment the mapping does, reconciled immediately on every mapping write and on every token exchange, so narrowing a binding revokes rather than merely looking like it does. `null` (omitted) and `[]` are distinct and deliberately so: a mapping created before this release, or one that simply never declares a binding, has an absent binding and behaves exactly as it always has — nothing reconciles and any hand-wired membership is left alone; `[]` is a declared assertion of "no memberships" and strips everything. A binding names groups by id, never creates one, and refuses a create or update that names a group that does not exist. `allowed_repo_ids` is unchanged and is now specified for what it always was: a ceiling that can only narrow what the binding confers, never widen it. See `docs/ci-oidc.md` for the adoption order (declare the binding, verify, then remove the hand-wired membership) and for why the mapping's `claim_filters` remain the security boundary an any-of filter and a broad binding compound.
