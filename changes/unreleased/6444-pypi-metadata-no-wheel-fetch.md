- **A PyPI `.metadata` request no longer downloads the whole wheel under `fail_closed`** (#6444). When a Remote's cached wheel had no usable scan verdict and its cached copy was stale, the PEP 658 metadata gate (#6439) ran the wheel's own download path: it re-read the upstream index and downloaded the whole wheel to answer a request for a few KB of METADATA, so a resolver reading many candidate versions paid one wheel download per candidate. The gate now runs the wheel's scan gate on the bytes already in the proxy cache, fresh or stale, and never contacts the upstream for the wheel. The metadata still follows the gate: a blocking verdict answers `403`, a scan that cannot conclude answers the wheel's `423`, and a cached body that cannot be read or does not match its sidecar's digest answers `503` with `Retry-After`. The scan is the one the wheel's own request joins or reuses, so the wheel is not scanned twice. Under `fail_closed`, while the cached copy is stale, the METADATA served is now the one inside the cached wheel the gate decided on (its `*.dist-info/METADATA`, or an sdist's `PKG-INFO`), not the upstream's `.metadata` sidecar, so the metadata always describes the bytes that were gated. It is served only when the Remote's cached index advertises exactly its hash (`data-core-metadata`); when the index advertises another (an upstream that reused the file name) or none, the request answers `503` with `Retry-After` until the wheel's own request has refetched and gated the new bytes, after which the new sidecar is served. A fresh cached copy still serves the upstream's sidecar. Status-code changes: while the upstream is unreachable, such a `.metadata` request answered the refetch's `502` and now answers from the gate on the cached copy; a stale cached distribution whose METADATA cannot be read answers `404` ("Metadata not available"), as the existing fallback does. There is no setting for this.
