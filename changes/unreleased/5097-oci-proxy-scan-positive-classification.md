- **OCI scan-on-proxy withholds a manifest it cannot classify under `fail_closed` instead of serving it unscanned** (#5097). The inline scan gate on a Remote OCI repository skipped every manifest it did not recognise as a runnable image, including ones it could not parse or classify. Container clients decode manifests more leniently than the server (case-insensitive keys, last duplicate key wins), so such a manifest could still run on the client. The gate now classifies positively: a manifest skips the scan only when no container runtime would run it (an index or manifest list, an artifact manifest, no config, no layers, the empty config, or no layer a runtime would unpack, which covers Helm charts, cosign signatures and attestations, SBOMs, in-toto, WASM and Flux artifacts). A manifest that does not parse, uses case-variant, non-ASCII or duplicate field names, or pairs a config that is not a recognised image config with a layer a runtime could unpack, is handled like an inconclusive scan: `423` under `fail_closed`, served with `X-AK-Scan: pending` under `fail_open` and record-only, and counted under its own `unclassifiable` verdict label. The same applies to a Remote member served through a Virtual repository, which now also refuses Docker schema1 manifests under scan-on-proxy as the Remote itself does. The scanner applicability check likewise keeps such manifests scannable. An artifact that pairs its own config with OCI image layers (a BuildKit registry cache exported with `image-manifest=true`, for example) is in that last group, so a `fail_closed` scanning Remote now withholds it.
