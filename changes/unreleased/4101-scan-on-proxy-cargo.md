- **Scan-on-proxy now gates `.crate` downloads from Cargo Remote and Virtual repositories** (#4101, part of #4097). Cargo repositories accepted `scan_on_proxy` but streamed every proxied crate unscanned. With the toggle on, a Remote crate download (from the upstream's `config.json` `dl` host) now goes through the shared inline scan-and-block gate: a vulnerable crate is refused with 403 `scan_blocked`, a clean one is served with `X-AK-Scan: clean`, the verdict is reused for the same digest, and fail-open (serve `X-AK-Scan: pending`, scan in the background) and fail-closed (423 until a verdict exists, including crates over the scan size cap) behave as they do for npm and PyPI. The scan grades the crate the client asked for: the name and version from the request must match the crate's own `Cargo.toml`, or the scan is treated as inconclusive. A Virtual repository applies the stricter of its own and each Remote member's policy, fetches from that member's own download host, and a member's block, quarantine hold or fail-closed lock is final rather than falling through to the next member. A crate whose bytes disagree with the sparse index `cksum` (the member's own index, on Virtual) is refused with 502 and evicted from the proxy cache, never served as clean. Sparse index and `config.json` responses are unchanged, and `GET /api/v1/formats` now reports Cargo as `scan_on_proxy: "enforced"`.
