section: Fixed
issues: [#5534]

- **A scan whose findings carry long version or source strings is stored instead of failing** (#5534). `scan_findings.affected_version`, `fixed_version` and `source` were limited to 100 characters (`affected_component` to 255, `title` to 500, `source_url` to 512), and findings are written in one batch, so a single advisory listing several fixed versions in one string failed the whole scan with `value too long for type character varying(100)` and dropped every finding it reported. Migration `339_scan_findings_text_columns.sql` changes those six columns to `TEXT`; on PostgreSQL 16 and later this is a catalog-only change (no table rewrite or index rebuild) that briefly takes an exclusive lock on `scan_findings`, waiting at most 5 seconds per attempt and retrying, and it drops and recreates the `scan_findings_effective` view in the same transaction. Two operator notes: if every lock attempt times out (about 35 seconds, for example behind a long-running transaction on `scan_findings`), the migration fails and the server exits at startup, leaving nothing half-applied, and the next start retries it; and because the column types change, a database connection that prepared a findings query before the migration answers `cached plan must not change result type` on every later execution, so during a rolling upgrade replicas still on the previous version can fail findings reads (findings list, policy evaluation, SBOM) until they are replaced or their pooled connections recycle (up to 30 minutes). A finding that still cannot be stored (a NUL byte, or a `cve_id` over 30 characters) now fails only its own scan, with an error message naming the finding and the column, and the remaining scanners for the artifact still run; before, the scan stayed `running` until the stuck-scan janitor failed it and the later scanners were skipped. The `source` findings filter now accepts values up to 1024 characters.
