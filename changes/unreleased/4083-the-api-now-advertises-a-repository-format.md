section: Fixed
issues: [#4083, #4085]
---
- **The API now advertises a repository format string that the API itself will accept back** (#4083, #4085). `repo_to_response` built the `format` field with `format!("{:?}", …).to_lowercase()`, which drops the underscore in multi-word variants, so three formats were served under names `parse_format_str` rejects: `conda_native` as `condanative`, `wasm_oci` as `wasmoci`, and `helm_oci` as `helmoci`. Found on a running deployment with two user-visible symptoms — the repository **renders as `GENERIC` in the UI**, because the client cannot match the format string and falls back, and feeding the API its own output is refused (`POST /api/v1/repositories {"format":"condanative"}` → `400 VALIDATION_ERROR: Invalid format: condanative`). The database was correct throughout; only the response value was wrong. Nine call sites now use the canonical `RepositoryFormat::as_key()` / `RepositoryType::as_str()` spellings that already existed, and a round-trip test over **every** `RepositoryFormat::ALL` variant — not just the three that happen to be multi-word today — keeps a future multi-word format from reintroducing it. **Clients string-matching `condanative`, `wasmoci` or `helmoci` must move to `conda_native`, `wasm_oci` and `helm_oci`**: the response schema is unchanged, but the value of an existing string field is corrected from one the API rejects to one it accepts.
