- **`/api/v1/admin/settings` now reports and changes only the settings that take effect, validates their ranges and audits every change** ([#5652]). `GET` showed `max_upload_size_bytes: 104857600` while `MAX_UPLOAD_SIZE` (10 GiB by default) was the limit enforced, offered an `allow_anonymous_download` switch that nothing read, and `POST` stored negative retention values and wrote no audit row. `GET` now reports the upload limit in force and the stale-peer threshold in force; `allow_anonymous_download` is gone from the schema. `POST` is a partial update: an absent field keeps its value, and the `GET` body can be posted back. `retention_days` and `audit_retention_days` must be `0..=36500`, `backup_retention_count` `1..=10000` and `edge_stale_threshold_minutes` `1..=10080`, or the request answers `400 VALIDATION_ERROR` naming the field and stores nothing. A different `max_upload_size_bytes` answers `400` (set `MAX_UPLOAD_SIZE`), as does `allow_anonymous_download` with any value (anonymous access is `guest_access_enabled` on `PATCH /api/v1/admin/settings/system`). Each changed field writes one `SETTING_CHANGED` audit row with the acting admin and the old and new value. The stored `edge_stale_threshold_minutes` now also drives the background stale-peer detector (it applied only to `POST /api/v1/admin/cleanup`); `PEER_STALE_THRESHOLD_MINUTES` still pins it, and a different value then answers `400`. See `docs/operations/system-settings.md`.

  **Upgrade note:** a client that sets `max_upload_size_bytes` (the web UI's upload-size editor) or sends `allow_anonymous_download` now gets `400`.
