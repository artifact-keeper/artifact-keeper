- **Packages with no recipe now yield their statically linked C libraries from the binaries themselves — SONAME, version banners and build-id — as visibly lower-confidence components** (#4046). Recipe-derived component recovery (#4033) covers packages whose recipe declares a source, which is most of conda-forge but not the channels that publish no recipe; that residue is statically linked code only the payload's bytes can name. Ingest now harvests ELF shared objects and executables from the conda payload walk (the same bounded walk that collects install scripts — same entry-count cap, same decompressed-byte budget, a new 32 MiB per-entry cap under which an oversized binary contributes its head) and a new `binary_catalog` service catalogs them from three signals in descending confidence order: **SONAME + version-banner agreement** (`detection_method: binary:soname+banner:<rule>`), **banner alone** (`binary:banner:<rule>`, the normal shape of a statically linked library inside an executable), and **SONAME alone** (`binary:soname`, identity without a version — the ABI tail is still never promoted into `version`). Banner rules are well-known patterns only — `banner-libwebp-v1`, `banner-openssl-v1`, `banner-zlib-v1` (the deflate/inflate banner, so a bare `1.2.13` does not match), `banner-libpng-v1` — each a named, individually tested rule in the `cpe_candidates` style, so a wrong component is traceable to the pattern that produced it. The GNU build-id is used strictly as identity: two payload files with one build-id catalog once, and it is never used for advisory matching. **The lower confidence is visible, not flattened**: binary-derived rows never rise above `inferred` (a bare SONAME is `unresolved`), the `detection_method` names the signals and the rule, and the two classes sit side by side in the same `package_vendored_components` table the Analysis tab already renders — no migration needed. Because banner matching has a real false-positive rate, it is spent only where there is nothing better: `record_analysis` suppresses `binary:` components when a parsed recipe declares sources. The false-positive rate is **measured, not assumed**: a fixture corpus of crafted ELF binaries — true positives beside truncated banners, similar-but-wrong strings (`libwebpages`), LibreSSL-vs-OpenSSL, and one deliberately counted genuine false positive (a banner embedded as data in another library) — asserts a measured precision floor of 0.90 (currently 0.909). Mach-O and PE payloads are deferred: `catalog_file` dispatches on magic bytes, so adding a format is a new parser and a new arm, not a restructure. The ELF reader is a minimal dependency-free section-table walk (SONAME from `DT_SONAME`, build-id from `.note.gnu.build-id`): the tree carries no ELF crate, and two bounded structures sit well below the complexity at which a new parsing dependency earns its `cargo audit` surface.
