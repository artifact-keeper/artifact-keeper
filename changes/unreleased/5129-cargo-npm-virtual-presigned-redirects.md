- **Cached Cargo crates and npm tarballs downloaded through a virtual repository are now answered with a presigned redirect when presigned downloads are on** (#5129). The virtual walk of every other format has redirected a Remote member's fresh proxy-cache hit since #1555. The Cargo and npm virtual downloads used a resolver with no redirect path, so with `PRESIGNED_DOWNLOADS_ENABLED=true` and a redirect-capable backend (`S3_REDIRECT_DOWNLOADS=true`) every cached `.crate` and `.tgz` still streamed through the backend, which cost backend CPU and cross-zone transfer on every CI pull. The resolver now tries the redirect first for a Remote member. It signs only after the fast-path gates pass on a single read of the entry's sidecar: the entry is fresh and present in storage, outside its Package Age Policy hold, allowed by the origin policy and by the stored scan verdict. A refusal only declines the redirect, and the request is then answered exactly as with presigning off, so a held entry is still the `409` and a stale entry is revalidated, never redirected. A `HEAD`, a hosted member and a member that scans on proxy (served through its inline scan gate) keep streaming. Redirected downloads are counted against the member as streamed ones are. Index files, packuments and metadata are unchanged.

  Presigned downloads stay off by default, and nothing changes unless `PRESIGNED_DOWNLOADS_ENABLED` is set. To keep streaming these downloads while other formats redirect, leave `S3_REDIRECT_DOWNLOADS` unset on the backend that serves them. Measured on MinIO in the `s3-presign-and-scrub-1120` tier, 20 warm downloads through a virtual: before, 20 `200`s whose bodies (4,700 bytes for npm, 5,700 for Cargo, 20 copies of the file) all passed through the backend; after, 20 `302`s and no file bytes through the backend. The saving scales with file size and request volume.
