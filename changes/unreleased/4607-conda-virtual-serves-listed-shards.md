- **A virtual conda channel serves every shard its CEP-16 index lists; a cold sharded solve that reaches `cuda-nvcc_linux-64` no longer fails with 404** (closes #4607). The virtual's merged shard index listed conda-forge's `noarch` shard for `cuda-nvcc_linux-64`, and a request for that shard through the virtual answered 404 while the member served it. The shard is 90 bytes: conda-forge removed the package's only `noarch` build, so its shard holds no records and one `removed` entry. The download path decided admission by decoding the shard and required at least one record whose name the virtual admits, so it refused the empty shard, and it answered a shard it could not decode with the same 404. pixi and rattler treat a 404 for a listed shard as fatal, so every cold sharded solve through a virtual whose closure touches `cuda-nvcc_linux-64` (pytorch, jax and much of the scientific stack) failed. Admission is now decided from the merged index itself: a shard request through a virtual rebuilds the same merge the index is served from and is answered from the source that merge took the name from (a hosted member's shard, or the remote member whose index listed it first), so the set of shards served is exactly the set listed. The record-name check stays only as a defence against a shard whose records name a package the virtual does not take from remotes (owned by a hosted member, or outside the allowlist); it now streams the shard and keeps only the names, so it cannot fail on a real shard's size. Outcomes are told apart: a shard refused by policy is 404 `Shard not found` (logged at `info`, or `warn` when a listed shard's records smuggle in a refused name); a listed shard the member cannot produce (does not decode, upstream fetch failure or 404, over the size ceiling) is 502 naming the member, and an unlisted shard while a member failed to merge is 502 too, never a 404 that tells the client the package does not exist. The ceiling on one upstream shard is raised from 8 MiB to 16 MiB, separately from the shard index's: the largest conda-forge shards measured are `linux-64/awscli` (848 KB compressed, 6.2 MB decoded) and conda-pypi's `noarch/boto3-stubs` is 713 KB compressed but 51 MB decoded, and conda 26.7.0/26.7.1 reject shards that decode past 16 MiB (conda/conda#16575). The red-team workaround (`disable-sharded` for the virtual) is no longer needed.
