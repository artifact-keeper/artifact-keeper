- **Eight concurrent anonymous conda repodata requests no longer deadlock the buffered-metadata proxy path for every format** (#4145, #4129). Serving a proxied `repodata.json` reserves 128 MiB (`LARGE_METADATA_MAX_BYTES`) from the process-wide buffered-metadata byte budget and holds that reservation until the response is built; the #4051 patch-generation attribution added in that PR then fetched `{subdir}/patch_instructions.json` through the same budgeted helper, taking a SECOND, untimed 8 MiB reservation from the SAME budget while the first was still held. The shipped default budget is 1 GiB — exactly eight worst-case repodata buffers — so eight concurrent requests reserved all of it and then each waited for bytes only the others could release, until the 120 s global request timeout or a client disconnect dropped them: an unauthenticated, eight-request stall of the *shared* buffered-metadata path (RPM repodata, npm packuments, the PyPI simple index, Debian `dists`), not just conda, that any caller could repeat at will and that a lowered `AK_PROXY_METADATA_BUDGET_BYTES` made cheaper still. The reservation is taken before the proxy cache lookup, so neither a cache hit nor a negative-cached 404 avoided it. The attribution fetch now runs BEFORE the repodata reservation exists rather than underneath it, so a request holds at most one permit from the budget at a time and its peak reservation falls from 136 MiB to 128 MiB; the attribution, the recorded rows and the `X-Repodata-Patch-Generation` header are unchanged, and the only cost of the order is one extra cached 8 MiB-capped attribution lookup when the repodata fetch itself then fails. A source pin keeps the two calls in that order and a budget model test proves that N nested reservations never complete while N sequenced ones do.
