- **Headless clients can sign in with the RFC 8628 device authorization grant** (#3461). A CLI, CI runner or other browserless client calls `POST /api/v1/auth/device/code`, shows its user a short code, and polls `POST /api/v1/auth/device/token`; the user enters the code on the `/device` page of a signed-in browser session, sees the requested scopes, and approves or denies. The client then redeems the device code exactly once for an AK access token and refresh token. This is a plain Artifact Keeper grant, not an OpenID Connect flow: the approver signs in however AK already allows, and no `id_token` is issued. The grant is off by default; set `DEVICE_AUTH_ENABLED=true` to turn it on (see `docs/device-authorization.md` for the settings).

  The issued pair is capped at the requested scopes that the approver may grant, never carries `*` or `admin`, and its refresh family takes part in rotation, replay detection and logout like any other session. Only an interactive session can approve: API tokens, service accounts, download tickets, Basic credentials and scope- or repository-restricted JWTs are refused. A redeemed code cannot be redeemed again, polls inside the interval get `slow_down` and a longer interval, codes expire after 10 minutes, and wrong user codes are throttled per user and per client IP. Code issuance, approval, denial, failed attempts, replayed codes, unredeemed approvals and token issuance are all audited, and neither code is stored in plaintext or written to the audit trail.
