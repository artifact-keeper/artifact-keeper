section: Fixed

- **An advisory-feed outage is no longer recorded as a completed clean scan** (#4080). `query_osv` and `query_github` logged a `warn!` and returned an empty result on transport error, non-2xx status and parse failure alike; `DependencyScanner::scan` then set `scan_completeness: Complete` unconditionally. A feed outage was therefore bit-for-bit indistinguishable from a genuinely clean package. Both feeds now report whether they answered (`query_osv_detailed` / `query_github_detailed`, added alongside the existing methods, which remain as flattening wrappers), and the scan is graded `Partial` when either did not. The distinction the fix turns on is "asked and refused" versus "not applicable": a GitHub **403** — a rate limit or a rejected token — degrades the scan, while an ecosystem the GitHub Advisory Database does not index and a deployment with no GitHub token configured do not, because in both of those nothing was ever asked.

  Two narrower false-cleans are closed with it, both of which a 200 could survive for the full hour-long cache TTL. An OSV response carrying **no `results` array at all** was read as a batch of empty results and cached as clean for every dependency in the chunk; it is now treated as unanswered. A response covering only a **prefix** of the batch left the remaining queries unanswered, and padding them with empty slots would cache "clean" for dependencies the feed never spoke about; those slots are now left unrecorded and uncached, and the lookup is degraded. (Failed lookups — transport error, non-2xx, unparseable body — never reached the cache even before this change; the issue text saying otherwise is wrong.)

  **Operator note — scans will start reporting `partial` during feed outages.** This is the intended behaviour and it is visible fleet-wide, so it is worth reading before upgrading rather than discovering in a dashboard. Before this release, an OSV.dev or GitHub Advisory outage produced `scan_completeness: complete` with zero findings on every dependency scan that ran during it. After it, those same scans are graded `partial`, which is persisted to `scan_results.scan_completeness` and surfaced in the SBOM document's completeness field and anywhere downstream attestation tooling reads it. Nothing about **findings** changes — a partial scan still reports everything the feeds did return — and no scan fails; what changes is that "we could not reach the feed" is now recorded as a distinct fact from "we asked and there was nothing". Expect a correlated burst of `partial` results during any OSV.dev incident, and note that alerting or gating keyed on `scan_completeness = complete` will now see those scans. A deployment with no GitHub token configured is unaffected: not consulting the GitHub feed is not an outage.
