section: Fixed
issues: [#5659, #5660]
---
- **Git LFS objects and MCP server versions are stored under repository-scoped keys on cloud storage, and an MCP approval that cannot store the version no longer answers `200`** ([#5659], [#5660]). On S3, GCS or Azure, Git LFS objects were written to the flat key `gitlfs/<oid[..2]>/<oid>` and MCP server versions and bundles to `mcp/<name>/<version>/...`, keys every repository shares. Pushing an LFS object another repository already held (a fork or mirror pushing the same object) therefore failed with `409 CONFLICT` "refusing cross-repository overwrite" (a regression in this release: 1.11.12 wrote the shared key without the cross-repository guard), and approving or publishing an MCP server version another MCP repository already held failed the same way. New objects now go to `gitlfs/<repository-id>/...` and `mcp/<repository-id>/...`; objects stored before keep serving from the key their row records, nothing is migrated, and filesystem storage and `STORAGE_KEY_SCHEME=flat` keep the flat keys. `POST /api/v1/repositories/{key}/mcp/catalog/{id}/approve` (and the pin route) also answered `200` when storing the ingested version failed, logging the error and never serving the version; it now answers the storage error (`409 CONFLICT` with the guard's message, `507 QUOTA_EXCEEDED`, or `500 STORAGE_ERROR`). The decision is still recorded and the next sync retries; an unreachable upstream still answers `200` with `ingestError`. See `docs/mcp-registry.md`.
