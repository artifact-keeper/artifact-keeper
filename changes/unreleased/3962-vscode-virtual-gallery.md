- **A virtual `vscode` repository now answers the gallery protocol by aggregating its members, so one `serviceUrl` can serve an organisation's own extensions and a proxied public gallery at once** (#3962). This is the configuration the single-`serviceUrl` constraint actually calls for, and until now no repository type could provide it: hosted members were not served by the gallery at all, and a remote member could only be configured as the editor's one gallery, which excludes everything internal. A virtual repository's `extensionquery` and latest-version routes now read every member the caller may see, in the operator's own priority order — hosted members from their artifact rows, paged by the client's own `pageNumber`/`pageSize` exactly as a hosted repository is, and remote members through the same plan a direct remote repository uses, so an update check (named identities with their version history) or an over-ceiling search is composed into its bounded equivalent rather than forwarded as a query Open VSX answers with tens of MiB — and merge the results, with the first member that knows an extension being the one that describes it. Putting a hosted member first is therefore how an internal extension shadows a public one of the same name. Each member's entries are rewritten onto that member's own routes, so a package or asset URL resolves through the per-member route that already serves it and the virtual repository needs no byte-serving route of its own.

  **Aggregation does not widen any member's visibility, and one bad member cannot take the page down.** Members go through `authorize_virtual_members`, the same read predicate a direct read applies (#1804) — and because a gallery client is anonymous, that means public members only, which is consistent with the gallery being public-only in the first place. A remote member that fails — no usable gallery upstream, an upstream error or timeout, a metadata-budget wait, a malformed or over-ceiling page, or an age gate that cannot be evaluated — contributes nothing and is skipped with a log line naming it and the status, while the other members' entries are still served; each remote member's own age gate and curation still apply to its own entries. One aggregation holds a permit of the gallery's composition admission bound from before the first member is read until the merged page is serialized, so anonymous callers cannot pile up unbounded multi-member pages; no byte reservation is held across the fan-out. At most eight members are read per query, since each remote member is an upstream round-trip. `TotalCount` is the sum of what the members reported, an upper bound while an extension exists in more than one of them, and the merged page is not re-sliced — members are already paged by the client's own `pageNumber`/`pageSize`, so a page may carry up to one page per member. The `vspackage` and `/asset/...` routes still answer `501` for a virtual repository, and nothing a virtual page emits points at them.
