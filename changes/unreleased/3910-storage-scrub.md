- **Storage scrub: detect, report, and (from a verified copy) repair corrupt content-addressed objects** (#3910). `POST /api/v1/admin/storage-scrub` (admin-only, body `{"repair": <bool>}` required, optional `max_objects`, `max_bytes`, `repository`) re-reads live artifact objects (content-addressed keys and `oci-manifests/*`) and `oci-blobs/*` through the repository's storage backend, including migration-mode fallback keys, hashes them incrementally, and records every mismatch or missing object in `storage_scrub_findings`, which you can list with `GET /api/v1/admin/storage-scrub/findings`. Each run is bounded by an object budget and a byte budget. Its cursor is saved after every object, so a run cut short by the request timeout resumes where it stopped; a repository-scoped run keeps its own cursor. A cluster-wide lock allows only one scrub at a time. A mismatch is only recorded after re-reading the row, so a concurrent republish, delete, or storage-GC reap is never reported as corruption. With `repair: true`, only objects in the content-addressed layouts (`ab/cd/<sha256>`, `oci-blobs/sha256:<hex>`, `oci-manifests/sha256:<hex>`) are restored, and only from another stored copy of the same digest that re-hashes correctly; the copy is written atomically and re-verified. Path-keyed objects (for example Maven) and objects without a verified copy are reported and never overwritten. Each run is audit-logged (`STORAGE_SCRUB_RUN`) when it starts, before any object is touched, and again when it completes, fails, or is cancelled (for example by the request timeout); both entries share a `run_id`. Protobuf module commit bundles are skipped as unverifiable, because their rows record the commit digest rather than the bundle's SHA-256. Set `STORAGE_SCRUB_INTERVAL_SECS` to also run a report-only pass on a schedule (disabled by default).
