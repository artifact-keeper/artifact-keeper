- **Lifecycle policies are now scoped by explicit repository assignments: a policy applies to all repositories, to a chosen list of repositories, or to none, and one policy can be reused across repositories** (#3794). Previously a policy's scope was a single nullable `repository_id`, where null meant every repository, so a policy could not be shared by a subset of repositories and a forgotten field silently widened a destructive policy to the whole instance. Policies now carry `applies_to_all` plus `repository_ids`, stored in a new `lifecycle_policy_repositories` join table (migration 233). `PUT`/`DELETE /api/v1/admin/lifecycle/{id}/repositories/{repository_id}` attach and detach one repository idempotently, `GET /api/v1/admin/lifecycle?repository_id=` lists the global and assigned policies for a repository, and `GET /api/v1/admin/lifecycle/capabilities` lets clients confirm the backend supports explicit assignment before they write scope. Every policy type now runs per resolved repository, so `max_versions` and `size_quota_bytes` also work under global scope, evaluated independently in each repository. Scheduled runs and execute-all skip policies with no assignment. The migration preserves existing behaviour: a policy with a null `repository_id` becomes `applies_to_all = true`, and a single-repository policy gets one assignment. The deprecated `repository_id` field is still returned, but only as a projection: it holds a UUID when the policy has exactly one assignment and is null otherwise, so null no longer means global. See `docs/lifecycle-policy-assignments.md`.
  **Upgrade note: stop every old backend replica and lifecycle scheduler before running migration 233. Do not do a rolling or mixed-version deploy.** Older binaries treat any policy that has no single `repository_id` as GLOBAL. That includes an unassigned policy and a policy assigned to two or more repositories. An old replica or scheduler still running during the upgrade could therefore delete artifacts across every repository. Helm upgrades are rolling updates by default, so scale the backend to zero (or otherwise stop all old pods) before upgrading. Downgrading to an older binary is unsafe unless you first reconcile policy scopes by hand. **Two API behaviour changes:** (1) creating a policy without `repository_id` (omitted or null) now creates a dormant policy that deletes nothing, not a global one; CLI, Terraform and other API clients that relied on the old default must send `applies_to_all: true`. (2) Deleting a repository no longer deletes its single-repository policies; it removes the assignment and leaves the policy dormant.
