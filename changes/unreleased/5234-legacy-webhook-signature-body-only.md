---
section: Fixed
issues: [#5648, #5234, #5297]
---
- **The legacy `X-Webhook-Signature` header is now `sha256=HMAC(secret, body)`, so a receiver can verify it** (#5648, backport of #5234, #5297). **This changes a value on the wire in a patch release:** a receiver that verifies `X-Webhook-Signature` as `HMAC(secret, "<t>.<body>")` stops verifying after upgrading to 1.11.14 (see "Am I affected" below). Since the v2 wire contract (#919) the header was meant to sign the raw body alone, as the webhooks documentation and the release-gate suite describe ("`sha256=<hex>`, no timestamp"), but it was computed over `"<t>.<body>"` and so held the same hex as the `v1=` token in `X-ArtifactKeeper-Signature`. The header carries no timestamp, so a receiver that read only `X-Webhook-Signature` and followed the documented form could never verify a delivery. `X-ArtifactKeeper-Signature` (`t=`, `v1=` over `"<t>.<body>"`, and `v2=`) is unchanged, and during a rotation overlap the legacy header still uses only the current secret. **Am I affected:** only if a receiver verifies `X-Webhook-Signature`. A receiver that follows the documented body-only form starts passing. A receiver that was written against the observed value, recomputing it over `"<t>.<body>"` with `t=` taken from `X-ArtifactKeeper-Signature`, fails after the upgrade: switch it to verify the `v1=` token in `X-ArtifactKeeper-Signature` (same inputs, and it adds replay protection) or to HMAC over the body alone. The legacy `X-Webhook-*` headers are deprecated and slated for removal; new receivers should verify `X-ArtifactKeeper-Signature`.
