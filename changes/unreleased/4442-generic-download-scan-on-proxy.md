---
section: Security
issues: [#4442, #4097]
---
- **The generic download route no longer serves around scan-on-proxy: while a repository scans, a proxied file of an enforced format is refused there** (#4442, part of #4097). `GET /api/v1/repositories/{key}/download/*path`, which also answers on `/general/{key}/*path` and backs the web UI's download button, streamed a Remote repository's proxy-cache or upstream bytes with no scan gate, for every format. The format routes (`/npm`, `/pypi`, `/cargo`, `/maven`, `/ivy`, `/nuget`, `/vscode` and `/v2`) gate those same bytes, from the same proxy cache, so a package they refused with `403` could be downloaded here. Because the buffered gate commits upstream bytes to the cache before it decides (#4365), a refused pull even left them warm for this route. The route cannot run the gate itself: the gate grades the package coordinate each format route parses from its own request shape, and npm and Cargo even fetch from a source their own metadata names, none of which this route has a parser for. So when a Remote repository of an enforced format has `scan_on_proxy` on, the route now answers `403` with `{"error": "scan_on_proxy_route_required", "file": ..., "handler": ...}` before any routing-rule read, cache read or upstream request, and `handler` names the format handler whose route serves the file through the gate (`sbt` is mounted at `/ivy`, `oci` at `/v2`). A Virtual repository refuses the same way, on this route and on `GET /api/v1/repositories/{key}/artifacts/*path` (which serves a Virtual member's bytes through the same member walk), when a Remote member the caller may read scans under the stricter-of-two rule, while a hosted member that owns the exact path is still served. An unreadable `scan_on_proxy` flag answers `503` instead of streaming unscanned.

  **Upgrade note: this is a deliberate behaviour change for repositories that scan on proxy.** It applies under every `proxy_scan_action`, `record_only` included, because that mode promises every pull is scanned and recorded, which this route cannot do. It applies to every path and to `HEAD`, which therefore no longer costs an upstream request, and it is stricter than the Maven route for POMs, `.xml` metadata and checksums: fetch those through the format route. A client that downloaded proxied files of such a repository through this route, the web UI's download button included, now receives the `403` and should use the format route. Files stored in the repository itself (`artifacts` rows) are served as before behind its download gate, and formats that do not enforce scan-on-proxy, or repositories with it off, are unaffected.
