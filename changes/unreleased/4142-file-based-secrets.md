- **Every credential-typed setting can now be read from a file via a `<NAME>_FILE` variable instead of the environment** (#4142). Following the `INITIAL_ADMIN_PASSWORD_FILE` (#2803) and `DEPENDENCY_TRACK_API_KEY_FILE` (#2084) precedent, `DATABASE_URL`, `JWT_SECRET`, `ADMIN_PASSWORD`, `OIDC_CLIENT_SECRET`, `LDAP_BIND_PASSWORD`, `OPENSEARCH_PASSWORD`, `PEER_API_KEY`, `SMTP_PASSWORD`, `GITHUB_TOKEN`, `MIGRATION_ENCRYPTION_KEY`, `SSO_ENCRYPTION_KEY`, `AK_WEBHOOK_SECRET_KEY`, `S3_SECRET_ACCESS_KEY`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN`, `S3_PRESIGN_SECRET_ACCESS_KEY`, `AZURE_STORAGE_ACCESS_KEY` and `AZURE_CLIENT_SECRET` accept a `_FILE` companion naming a mounted secret file (Docker/Kubernetes secrets, Vault agent templates), so those values no longer have to be readable from the process environment. The direct value wins when both forms are set, file contents are trimmed of surrounding whitespace, and a `_FILE` pointing at an unreadable or empty file is an error naming the variable and the path (never the contents) rather than being silently treated as unset. Documented in `.env.example` and `docs/operations/file-based-secrets.md`.
