- **A remote repository's upstream filter now also gates the curation upstream sync and the admin `test-upstream` probe** (#840). The filter (`include_patterns` / `exclude_patterns`) already gated every proxy fetch and the npm `/-/` and audit passthroughs, but curation sync walked its upstream index, and downloaded PyPI distributions for attestation verification, without consulting it, and the admin connectivity probe sent its HEAD regardless. The RPM (`repomd.xml`, `repomd.xml.asc`, `primary.xml`) and Debian (`Packages.gz`, `Packages`) index fetches, and the PyPI provenance, JSON and distribution fetches, now match the filter against the same subject the proxy would use (the upstream-relative path, or the full URL for a fetch outside the upstream base): a refused fetch is skipped without a request, the staging repo is left unsynced rather than failed and stays unstamped so a filter change applies on the next tick, and a refused attestation lookup leaves the package unverified instead of falsely verified. `POST /api/v1/repositories/{key}/test-upstream` requests the upstream root (subject: the empty path), so an include-only filter refuses it with 404 unless a pattern admits the root. A package the filter refuses is also not ingested into the curation catalog even when the index listing it is admitted, so the catalog never advertises packages the remote will not serve (existing catalog rows are left as they are). A repository with no filter is unaffected. The npm upstream change feed remains outside the filter: it is a single global subscription, not a per-repository upstream fetch.
