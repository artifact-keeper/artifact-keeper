section: Security
issues: [#4452]

- **The repository API no longer returns a Remote's upstream credentials when they are embedded in `upstream_url`** (#4452). A Remote created with `https://user:password@host/...` had the URL echoed back verbatim, password included, by the create response, `GET /api/v1/repositories`, `GET /api/v1/repositories/{key}` and the update response, so any caller with read access to repository metadata could read a live upstream secret. Every response that carries the URL now renders it with the userinfo removed and reports a new boolean `upstream_url_has_credentials` (additive field) so a client can still tell that credentials are configured. The same redaction applies to the `POST /api/v1/repositories/{key}/test-upstream` response, to the `origin.upstream_url` of artifact detail responses (the origin record of a proxied artifact is derived from the repository's upstream URL), to `upstream_url` / `index_upstream_url` values in audit-entry details, and to two log lines that printed the raw URL. Writes are unchanged: a URL with userinfo is still accepted on create, still stored as given, and the credentials are still sent upstream as HTTP Basic auth, so existing Remotes keep authenticating. To keep a secret out of the URL entirely, configure it with `upstream_auth_type` / `upstream_username` / `upstream_password` (or `PUT /api/v1/repositories/{key}/upstream-auth`), which are stored encrypted and never returned.
