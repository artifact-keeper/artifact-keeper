section: Changed
issues: [#4182]
---
- **A burst that uses every database connection no longer slows every request down together: admitted requests finish in bounded time, the overflow is answered `503` with a `Retry-After` that predicts the backlog, and readiness stays green** (#4182). Each query takes its own connection from a first-come-first-served pool, so with far more requests in flight than connections every request waited behind the whole crowd until clients timed out, a request that reached `DATABASE_ACQUIRE_TIMEOUT_SECS` (5 s) got `503 POOL_EXHAUSTED` only then, and `/readyz`, on the same pool, reported a busy replica not ready.

  Two default changes. A router-wide admission gate now runs before any authentication or handler work: at most `DATABASE_REQUEST_CONCURRENCY` requests (default four per pool connection) run their handler phase while the pool is busy. Past that a request queues for a slot for up to `DATABASE_REQUEST_ACQUIRE_WAIT_MS` (default 2000); one whose predicted wait (queue ahead x average slot hold / slots) is longer is answered the same `503 POOL_EXHAUSTED` body at once with a `Retry-After` (1 to 30 s) predicted from the queue plus the clients already told to come back, so returning clients are spread out, counted in the new `ak_db_requests_shed_total`. The gate sheds nothing while the pool has room, and never touches health, readiness, liveness or `/api/v1/admin/metrics`. A shed request has done no work, so it is never let through: authentication and scanning run unchanged for every admitted request. Set either variable to `0` to turn the gate off. And `/health` and `/readyz` now read the database through their own one-connection pool, so they report whether the database answers rather than whether the request pool is busy; that connection counts toward the Postgres connection budget, one more per replica, and `DATABASE_PROBE_CONNECTIONS=0` makes the probes share the request pool as before. Because a wedged request pool no longer fails readiness, alert on `ak_db_requests_shed_total` (and keep alerting on `ak_db_pool_connection_failures_total{stage="request"}`). A shed upload may show up as a broken pipe on clients that send the body without waiting for `100 Continue`. The trade-off: in a burst that queueing would have cleared within the clients' patience, the fleet's wall time can be longer (about 15 % in the measured 24-installer run at +2 ms per database round trip) in exchange for served requests answered in about 2 s instead of 9 s; in a burst past the clients' timeouts the fleet finished in half the time. The measurements, the connection-budget formula and a worked sizing example are in `docs/operations/load-shedding.md`.
