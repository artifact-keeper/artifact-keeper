section: Changed
issues: [#4182]
---
- **A burst that uses every database connection is answered `503` with `Retry-After` within half a second, and readiness stays green while it lasts** (#4182). Under a fleet of package installers each request needs a pooled connection, and when none was free a request queued until `DATABASE_ACQUIRE_TIMEOUT_SECS` (5 s) ran out before it got `503 POOL_EXHAUSTED`. Every overflow request stalled for the whole timeout, and `/readyz` queued on the same pool, so a replica that was busy, not broken, reported not-ready and was taken out of service.

  Two default changes. A router-wide admission gate now runs before any authentication or handler work: at most `DATABASE_REQUEST_CONCURRENCY` requests (default four per pool connection) run their handler phase while the pool is busy, so an admitted request queues behind a bounded crowd instead of the whole burst; a request that cannot get a slot within `DATABASE_REQUEST_ACQUIRE_WAIT_MS` (default 500) is answered the same `503 POOL_EXHAUSTED` body with `Retry-After: 1` at once, counted in the new `ak_db_requests_shed_total`. The gate sheds nothing while the pool has room. A shed request has done no work, so it is never let through: authentication and scanning run unchanged for every admitted request. Set either variable to `0` to turn the gate off. And `/health` and `/readyz` now read the database through their own one-connection pool, so they report whether the database answers rather than whether the request pool is busy. That connection counts toward the Postgres connection budget, one more per replica; `DATABASE_PROBE_CONNECTIONS=0` makes the probes share the request pool as before. If you alert on `ak_db_pool_connection_failures_total{stage="request"}` to spot an undersized pool, add `ak_db_requests_shed_total`: most saturation now shows there. The connection-budget formula and a worked sizing example are in `docs/operations/load-shedding.md`.
