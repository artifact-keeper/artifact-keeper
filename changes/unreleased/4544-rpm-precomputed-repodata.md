- **Hosted RPM repodata is built in the background and served from storage** (#4544). A hosted RPM repository used to render a root's `repomd.xml`, `primary.xml.gz`, `filelists.xml.gz` and `other.xml.gz` on the first request after every change, on every replica: about 35 s of CPU for a 2,500-package root, and nearly every request during a bulk import. Now a change marks the root dirty (migration 308, triggers on `artifacts` and `artifact_metadata`), and a background builder renders it once the root has been quiet for 3 s, or after at most 60 s of continuous writes (`RPM_REPODATA_BUILD_QUIET_SECS`, `RPM_REPODATA_BUILD_MAX_DELAY_SECS`). One replica builds each root under a cluster lease. The documents are stored under `repodata/<repository id>/<root>/<revision>/` in the repository's storage, and every replica serves them from there; `repomd.xml.asc` is still signed per request, so a key rotation applies at once. The stored bytes are the ones the on-request render produces for the same packages. A root that has not been built yet (every root right after the upgrade) renders on request as before until its first build. The previous revision is kept for clients in the middle of a refresh and older ones are deleted. **Behaviour change:** right after an upload or a delete, a hosted repository's repodata can describe the previous state for a few seconds, until the builder catches up. Virtual repositories, curated publications (`@N`) and remote repositories are unchanged.
