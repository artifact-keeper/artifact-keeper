section: Security
issues: [#5450, #5451]
---
- **The introspection worker correlates every MCP response with the request it answers and accepts a session id only from `initialize`** (#5450, #5451). Previously a malicious streamable-HTTP/SSE server could answer discovery or `tools/list` with a response for another request id and the probe still succeeded with the tools it carried, and it could assign an `Mcp-Session-Id` before `initialize` or replace an established one mid-session. A response whose `id` is missing or differs in type or value, a second response to an answered request, a batch carrying a response, an `initialize` session id that is not 1-256 visible ASCII characters, or a later response naming a different session now end the probe `refused` with `details.protocolViolation` (`response_id_mismatch`, `duplicate_response`, `unexpected_batch`, `session_id_invalid`, `session_id_changed`), and nothing from that probe is stored as the server's capabilities. A session id offered outside the `initialize` response is ignored and never sent. A non-2xx body that is only an HTTP-level error (such as the `"id": "server-error"` 400 the MCP Python SDK v1.x sends before `initialize`) is judged by its status alone, so those servers still fall back to `initialize`.
