section: Added
issues: [#3812, #2386]

- **Repositories have a visibility axis: `public`, `internal`, or `private`** (#3812). Access was a single boolean, `repositories.is_public`, which could express "anyone including anonymous" or "grant holders only" and nothing in between — leaving no way to say "readable by every authenticated principal", the state most repositories on a corporate instance actually need. `visibility` is now the authoritative field, persisted independently of any server-wide flag. `internal` grants a READ baseline to any resolved principal and confers no write, delete, or administrative capability — including filing a promotion-approval request, which still needs an explicit grant on the source repository; it is invisible to anonymous callers on every surface (REST, native protocols, OCI `/v2`, listing, search). For every decision other than read authorization it behaves exactly as `private`, including the repository-scoped-token ceiling: a token whose allow-list excludes an internal repository is still refused, because an anonymous caller gets nothing from one and so there is no credential-free baseline for a scoped credential to have fallen below.

  The API is additive. `visibility` is the new field on the create, update and read shapes; `is_public` and its alias `allow_anonymous_access` remain accepted and returned, and mean exactly `visibility == "public"`. A client that speaks only the boolean — the out-of-tree Terraform provider, an older SDK — keeps working unchanged and simply reads an internal repository as not-public. Supplying `visibility` and the boolean with contradictory values is rejected with a 400 rather than silently resolving to one of them. With guest access disabled, a request for `public` is still refused with a 400 (#3855); a request for `internal` is accepted, since it never asks for anonymous access.

  Blast radius reports a fourth access scope, `internal` (#2386): `classify_access_scope` had only `public`, `restricted_acl` and `restricted_roles`, so an internal repository would have been reported as restricted — telling an operator triaging a CVE that a vulnerable artifact reached a handful of grantees when every principal on the instance could pull it. The accessible-users endpoint likewise reports `exposure: everyone` for an internal repository instead of enumerating the whole user table. The audit log's `RepositoryDetails.visibility` now records the authoritative state rather than deriving `"public"`/`"private"` from the boolean, which would have recorded internal repositories as private.

  **Upgrade note — one manual review step.** Migration 245 backfills `is_public = true -> 'public'` and `false -> 'private'`. No repository becomes `internal` automatically and no repository's audience changes: the upgrade is exactly access-preserving in both directions. Repositories that were *meant* to be internal but were coerced to `is_public = false` by the pre-#3855 guest-access rule are indistinguishable from ordinary private ones, and that intent cannot be recovered from the data; identify them from your own records (the audit log's `RepositoryCreated`/`RepositoryUpdated` entries carry the requested value). Instances that have always run with guest access enabled need no action. Separately, to narrow a specific `public` repository to `internal`, list the candidates with `SELECT key, name, created_at FROM repositories WHERE visibility = 'public' ORDER BY key;` and change each one through the API (`PATCH /api/v1/repositories/{key}` with `{"visibility": "internal"}`) rather than a raw `UPDATE`, so the change is recorded in the audit log and propagated to every serving instance.
