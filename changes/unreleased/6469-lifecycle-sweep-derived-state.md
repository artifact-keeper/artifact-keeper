- **A lifecycle or retention sweep now updates each format's derived state the way a single delete does** (#6469, from the #6333 audit). A sweep soft-deletes in bulk SQL, so it skipped most of what the per-artifact delete does after its commit. After a sweep, a Maven repository kept serving the `maven-metadata.xml` that `mvn deploy` uploaded, still listing the swept versions in `<versions>`, `<latest>` and `<release>`, and the stored SNAPSHOT document still named swept builds. The swept crate versions stayed in the Cargo sparse index (cached for up to 300 s) on the repository and on every Virtual over it. Push and mirror peers were never told to delete. No `ARTIFACT_DELETED` audit row was written, no `artifact.deleted` event (and so no webhook or email) was emitted, and with OpenSearch configured the swept artifacts stayed in search results. A sweep now does all of this for the rows it removed. It costs one scan for the swept ids, then a fixed number of statements and one OpenSearch `_bulk` request per 500 artifacts, and the Maven and Cargo work once per package in each page. The work is recorded in the sweep's own transaction (migration 424) and done page by page, so a restart part-way through is resumed on the next lifecycle tick: each swept artifact gets exactly one peer delete task and one audit row, and its event at least once. The events are paced, so a large sweep no longer makes webhook, email or search consumers drop other events. A row that is restored or uploaded again before its page is left alone. The REST artifact delete now drops the Cargo index cache too; until now only a publish did.

  Not covered yet, and tracked on #6489: the OCI manifest reference rows a sweep leaves behind (they delay blob GC, and serving already hides them), and the native Helm and Conan bulk deletes, which skip the same steps.
