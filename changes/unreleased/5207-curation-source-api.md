- **A staging repository's curation source can be set through the API, and a curation sync with nothing to do no longer reports success** ([#5207]). No request field wrote `curation_source_repo_id`, the column that links a staging repository to the Remote its curation sync ingests from, so a staging repository made through the API could not ingest anything, and `POST /api/v1/curation/repos/{key}/sync` still answered `200` with `"succeeded": true`. `POST /api/v1/repositories` and `PATCH /api/v1/repositories/{key}` now take `curation_source_repository_key`: the key of a Remote repository of the same format (or the same package family: `pypi`, `poetry`, `jupyter`; `npm`, `yarn`, `pnpm`) that the caller can read, on a staging repository whose format has a curation sync (rpm, debian, and the PyPI and npm families). `""` removes the link on `PATCH`. Anything else is a `400`, and a Remote the caller cannot read answers exactly like one that does not exist. The link is read back as `curation_source_repo_id` on the repository. The sync trigger now answers `409` with the reason when a pass would do nothing: the repository is not a staging repository, its format has no curation sync, curation is not enabled on it, it has no curation source, the source has no upstream URL, or the source's upstream URL is one the upstream URL validation refuses (the sync skips it without a request). The config-as-code document (`GET /api/v1/admin/config/export`, `POST /api/v1/admin/config/import`) carries the link as `curation_source_repository_key` and applies a staging repository after its source.
