- **Conda artifacts now carry a publisher identity that `publisher_trust` curation rules can gate on, derived from verified CEP-27 provenance** (#4049). Conda was explicitly asserted not-applicable for publisher trust alongside maven/generic/docker — reasonable while conda had no attestation story, but stale since CEP-27 verification (#4048) and the `curation_packages.attestation_*` record (migration 195) exist. The verified path mirrors PyPI exactly: a verified CEP-27 record's cert-bound repository owner (the Fulcio certificate's GitHub org/user, issuer-checked against the OIDC allowlist) reaches the evaluator through the trusted server-side verification marker and satisfies `publisher_trust match: "attestation"` — including on re-evaluation, where the persisted record is rehydrated. The metadata fallback is the self-asserted `about.json` `maintainer` / `maintainers[]` string, always labeled `Metadata` and `verified = false`: it can satisfy only an explicit `match: "metadata"` opt-in, never a verified-publisher gate. Conda deliberately has no unverified-attestation middle tier: CEP-27 has no claimed-publisher field (which is why `Check::PublisherOwnerBound` does not exist for conda), so a stored-but-unverified attestation blob carries no honest publisher name, and its presence never upgrades a metadata identity. The ingest-time marker stripping that makes a self-asserted verification record a forgery rather than a bypass applies to conda rows unchanged.
