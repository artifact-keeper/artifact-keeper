- **Conda version ordering, version-spec matching and MatchSpec parsing now come from the rattler crates — the same implementation the pixi/prefix.dev client tooling is built on — so registry-side decisions agree with the client by construction** (#4040). Conda semantics used to be hand-rolled in three places, and each disagreed with the client in a place that matters: the generic curation comparator (`curation_service::version_compare`, split on `.`/`-`, numeric-when-possible) ordered a pre-release *above* its release (`"0a" > "0"` lexicographically), ordered an epoch *below* every epoch-less version (`"1!2" < "2"`), and ordered `1.0+local` above `1.0` — while conda orders letters below numbers inside a segment, so `1.0a < 1.0`, `1!2.0 > 2.0` and `1.0+local < 1.0`. A version-constrained curation rule is a vulnerability/policy match, and a rule the client would match but the registry does not is a silent miss. A new `conda_semantics` module wraps `rattler_conda_types` (`Version`, `VersionSpec`, `MatchSpec`) and now serves: conda-format curation rule evaluation (the typed dispatch routes `conda`/`conda_native` pattern rules to conda's ordering; every other format keeps the generic comparator byte-for-byte), and MatchSpec name extraction in the environment lockfile parser. The `.conda` (v2) container reader (`extract_conda_v2_metadata`) is migrated to `rattler_package_streaming`'s `stream_conda_info`, with the info tar still walked by the shared bounded walk — all three #2556 ingest caps apply unchanged, and the decompressed ceiling moves from a private 100 MiB buffering cap to the shared 128 MiB streaming budget the v1 path already uses. Deliberately NOT migrated, with the reason pinned by a test: the v1 `.tar.bz2` readers stay on our `MultiBzDecoder` path because `rattler_package_streaming` decodes bzip2 single-stream and cannot read a pbzip2/lbzip2-written package whose `info/index.json` sits past the first stream boundary (#4067 — the differential test asserts the reference implementation fails on the two-stream fixture, so a future rattler release that fixes it turns the test red and the migration can be revisited); repodata.json generation stays hand-rolled JSON because it is served byte-for-byte and rattler's `PackageRecord` serialization is not byte-identical to it; `current_repodata`/latest selection keeps its created-at ordering; and `rattler_index`/`rattler_repodata_gateway`/`rattler_lock` are not adopted. The migration is guarded by a differential harness that must pass against both implementations: a version-ordering corpus (epochs, pre/post/dev releases, local segments, separator equivalence, total-order spot checks) pinning the exact points where the old comparator disagreed with the reference, a MatchSpec corpus pinning the extracted name for every spelling the old extractor documented plus the one divergence found (`numpy. >=1.0` — the old walk trimmed the trailing dot and linked the edge to `numpy`; the reference reports `numpy.` as written, which matches no real package, so the edge is now recorded unresolved instead of silently linked), a container-streaming parity test for the v2 path, and a golden served-repodata test that uploads a fixture channel (one `.tar.bz2`, one `.conda`) through the real pipeline and asserts `repodata.json` and `current_repodata.json` are byte-identical to the pre-migration output — which they are, with zero differences to explain. Both new dependencies are BSD-3-Clause and build under the pinned Rust 1.98 toolchain; `rattler_package_streaming` is taken with default features off, so its reqwest networking module is not pulled in.
