- **An administrator can export the instance's repositories as one config document, and plan or apply it on another instance** (#5292). `GET /api/v1/admin/config/export[?repositories=a,b]` returns a versioned JSON document (`schema_version: 1`) with every repository keyed by `key`, sorted, with its per-repository settings: name, description, format, type, visibility, upstream URL, quota, promotion-only and versioning flags, custom User-Agent, curation flags, virtual members with priorities, and for remotes the cache TTL, `on_upstream_not_found`, the stale-if-error grace override, the upstream filter, routing rules, the egress proxy, upstream auth and the npm scope policy. No credential is exported: upstream passwords and tokens, and userinfo in upstream and egress proxy URLs, appear as `{"secret_ref": "<kind>/<key>"}` placeholders. `POST /api/v1/admin/config/import?mode=plan|apply` takes the document plus a `secrets` map: `plan` reports what would be created, updated, left unchanged and what the target has that the document does not mention, and lists missing secrets and changes an import cannot make; `apply` creates and updates through the regular repository routes (so validation, SSRF checks and per-repository audit rows are the usual ones), non-virtual repositories before virtual memberships, is idempotent, never deletes (`prune=true` answers 400 for now) and records one `CONFIG_IMPORTED` audit row. A `schema_version` other than 1 is refused. Scan policies, curation rules, the age gate, lifecycle, promotion and sync policies and permissions are not covered yet. See `docs/config-as-code.md`; a JSON Schema is at `docs/schemas/config-document.v1.json`.
