section: Fixed
issues: [#6000]
---
- **OpenSCAP scans now evaluate the container image they are recorded against, not the OpenSCAP sidecar's own filesystem, and no longer swap the configured profile for another** (#6000). The backend used to write the artifact's raw bytes (for an image, the manifest JSON) into the scan workspace as one file. The wrapper found no `etc/` there, so `oscap` ran its probes against the sidecar's own `/`. Every image, RPM and DEB got the same findings, which described the sidecar. The fix:
  - The backend now unpacks the image's layers from the repository's own blob store into a root filesystem, applied in manifest order with whiteouts honoured. An image index resolves to its runnable platform manifest. Unpacking is bounded by the scan-workspace ceilings (`MAX_SCAN_EXTRACTED_BYTES`, 200,000 entries, and the 10 GiB scan input limit). Every path resolves inside the image root with chroot semantics, symlinks are rewritten to relative targets that stay inside it, hard links must name a file inside it, device nodes are skipped, and setuid and setgid bits are dropped.
  - The wrapper evaluates that tree with `OSCAP_PROBE_ROOT`. oscap 1.3 has no `--chroot` option, so the wrapper's old `--chroot` branch could only fail. Its probes `chroot(2)` into the root, so the non-root sidecar starts `oscap` in a user namespace.
  - The datastream is chosen from the image's own `os-release`, with no fallback to another OS's content.
  **Results change on upgrade, because scans now evaluate the right thing.** Container images get findings about their own configuration. RPM and DEB packages, and OCI artifacts that are not runnable images, are now `not_applicable`, because a compliance profile evaluates an operating system and a package is not one. A scan that cannot be evaluated is also recorded `not_applicable` with the reason, never as a pass. That covers an image whose layers are not stored in the repository, one with no `os-release`, an OS no shipped datastream describes (the image ships RHEL 9 and CentOS Stream 9 content), and a profile in which no rule applies. Rules that check file owners or group owners are reported as not evaluated, because the unpacked tree cannot keep the image's ownership. An error from the wrapper now fails the scan; it used to be logged and the scan completed with zero findings.
  **Profiles.** The default `OPENSCAP_PROFILE` was `xccdf_org.ssgproject.content_profile_standard`, which neither shipped datastream defines, so the wrapper silently ran `anssi_bp28_enhanced` instead. The default is now `xccdf_org.ssgproject.content_profile_cis_server_l1` (CIS Level 1 - Server), a generic baseline both datastreams define. A configured profile that no shipped datastream defines now fails the scan, and the error lists the profiles that exist. A configured profile that does exist is used unchanged. The variable name is unchanged.
  **Upgrade together.** Run the OpenSCAP image from the same release as the backend. The new backend refuses an old wrapper's answer, which carries no scan status, and fails those scans instead of recording the old wrapper's findings.
  **Getting real results.** oscap's probes `chroot(2)` into the unpacked tree, and the sidecar runs as UID 1001. There are three ways to make that work, described in `docs/openscap-scanning.md` and in comments in `docker-compose.yml`:
  - Rootless Podman works out of the box: the wrapper starts oscap in a user namespace.
  - Allow unprivileged user namespaces for the sidecar, for example with `security_opt: [seccomp=unconfined]`. Docker's default seccomp profile blocks them.
  - Use the new opt-in root mode: start the sidecar with `user: "0"` and set `OPENSCAP_RUN_AS_ROOT=true`. Only the HTTP wrapper runs as root. Each scan's oscap process drops to UID 1001 before exec, keeping only `CAP_SYS_CHROOT` (plus `CAP_DAC_READ_SEARCH` when the container is given it, so mode-0000 files such as `/etc/shadow` can be read), with its capability bounding set reduced to match and `no_new_privs` set.
  On stock Docker with none of these, every OpenSCAP scan is recorded `not_applicable` with that reason, never as a pass.
