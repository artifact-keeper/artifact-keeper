section: Changed

- **A cold PyPI `.whl.metadata` no longer re-reads the upstream index when the client's index is cached, and the client-facing index is fetched gzip-coded** (#5983). Resolving a Remote sidecar or file read the project's whole upstream simple index even when the client had just been served that index from the proxy cache, so uv's first sidecar for each project paid a second full index download. Resolution now reads the project's index from the proxy cache while that entry is fresh (the PEP 691 JSON form uv asks for, then the HTML form pip asks for) and goes to the upstream only for a file the cached index does not name (one published since it was cached), for an index whose URLs are relative, or when nothing fresh is cached. It is never staler than the index the client resolved from. The client-facing simple index, the simple root and the legacy JSON API are now fetched from the upstream with `Accept-Encoding: gzip` (about a fifth of the bytes for a large index), decoded under the existing 128 MiB `LARGE_METADATA_MAX_BYTES` cap before they are rewritten and cached, and their revalidation probes replay the coding. A body that would inflate past the cap, a corrupt one or an unsupported coding is refused with a `502`. These documents are always rewritten, so clients still receive an uncoded body; distribution downloads and sidecars keep `identity` (#2915). The resolver index read already asked for gzip (#6353) and concurrent cold reads already shared one fetch (#6047). Default change: upstreams of PyPI Remotes now see `Accept-Encoding: gzip` on index requests. There is no setting for it; an upstream that cannot serve gzip correctly answers identity, which is accepted unchanged.
