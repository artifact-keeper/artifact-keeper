- **Virtual repositories answer `404` for a member's permanent upstream `4xx` and `503` only for a member's `5xx` or timeout, on artifacts and checksums alike** (#5504). The Maven virtual checksum walk counted every non-`404` member answer as a failure, so a Remote member whose upstream answers `403` for a missing key (S3-hosted Maven buckets do) or `401` for stale credentials turned every `.sha1`/`.md5` no member has into a `503` that clients retried forever; a permanent upstream `4xx` or a rejected path is now a miss, and only an upstream `5xx`, a timeout or transport failure, or a fault on the server's own side counts as the member being unavailable. A hosted member that has the artifact row but whose storage read fails now counts as unavailable too, where it read as a miss. The shared artifact walk behind most formats' virtual downloads (Maven, sbt, npm, Cargo, Conda, Debian, Go, Composer, Hex, Alpine, Chef, Git LFS, JetBrains, Protobuf, Terraform, VS Code, the generic route, and the scan-aware walks of Conan, CocoaPods, Pub, Swift and RubyGems) used to read a member's upstream `5xx` as a miss, so `lib-1.0.jar` answered the `404` Gradle caches while `lib-1.0.jar.sha1` answered `503`; it now passes over an unavailable member exactly as over a missing one, still serves from a lower-priority member that has the file, and answers `503` instead of `404` only when nothing served and a member was unavailable. A member's quarantine or policy block, and a Maven member's age refusal, still take precedence.
