- **Proxy scanning can now record findings without blocking pulls: `proxy_scan_action = record_only`** (#3645, #3868). Until now, scanning proxied artifacts and blocking them were one switch, and the default `block_on_policy_violation = false` meant "block on any finding", so a repository could not get vulnerability visibility on proxied packages without also failing builds. Setting `proxy_scan_action` to `record_only` through `PUT /api/v1/repositories/{key}/security` scans and records every proxied pull exactly as enforcement does (the `proxy_scan_results` verdict, per-CVE findings and SBOM inventory), but never withholds one. A vulnerable artifact is served on every pull with `X-AK-Scan: recorded`, a first pull is served `X-AK-Scan: pending` while the scan runs in the background, and an object over the scan byte cap or a scan that cannot finish is served pending rather than answered with 423. `record_only` overrides `block_on_policy_violation` and `severity_threshold`, and switching back to `fail_open` or `fail_closed` changes only whether pulls are blocked, not what was recorded. It applies to every format that enforces scan-on-proxy, including the OCI manifest gate and its layer blobs. On a virtual repository the result is `record_only` only when every side with proxy scanning enabled chose it, so an enforcing member is never relaxed by a record-only virtual, and a record-only member behind an enforcing virtual follows the virtual's threshold. An unrecognised `proxy_scan_action` (for example `record-only` or `fail-closed`) is now rejected with 400 instead of silently becoming `fail_open`. Every change to a repository's scan configuration (scanning on or off, `block_on_policy_violation`, `severity_threshold`, or `proxy_scan_action`) is audited as `REPOSITORY_UPDATED` with the configuration before and after the change and the names of the fields that changed. Migration 256 adds `record_only` to the column's allowed values.

  The reporter of #3868 ran with `severity_threshold = critical` and `block_on_policy_violation = false` and expected nothing below critical to be blocked. That configuration blocks by design: `block_on_policy_violation = false` does not mean "don't block". It means the threshold is off, so the gate blocks on any finding. Set `block_on_policy_violation = true` to enforce the threshold, or use `record_only` to stop blocking altogether.
