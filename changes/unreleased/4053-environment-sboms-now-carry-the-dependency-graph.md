- **Environment SBOMs now carry the dependency graph — one document per platform, with dependency edges, not a flat component list collapsed across platforms** (#4053). An SBOM that only lists components answers "what is here"; the graph is what makes a finding actionable ("libwebp is vulnerable *and it is here because you asked for pillow*"), and a conda environment is N graphs, one per subdir — `depends`/`constrains` resolve differently per platform, so one document covering `linux-64` and `osx-arm64` at once is wrong for both. The new `environment_sbom` service module renders the parsed lockfile graph of #4052 (`LockedEnvironment`: per-scope packages and resolved `dependant -> dependency` edges) as SBOM documents, **one per (environment, platform) scope**, with no cross-platform edge leakage by construction: no scope's generator ever sees another scope's rows, and a package present on `linux-64` but not `osx-arm64` has no node and no edge in the osx document. CycloneDX 1.5 expresses the graph as `dependencies[].dependsOn` over bom-refs with the environment itself as `metadata.component` (type `platform`); SPDX 2.3 as `DEPENDS_ON` relationships below an `SPDXRef-Environment` package the document `DESCRIBES`. Conda components are identified by the #4041 qualified purl — `pkg:conda/name@version?build=…&channel=…&subdir=…` — which *is* the bom-ref, so two builds of one name/version on two subdirs are two components with two stable ids; pypi/npm/cargo components use their conventional purl types, and a package whose coordinates cannot form a purl (no recorded version) falls back to a ref derived from its lockfile key, with uniqueness enforced rather than assumed. Edges come only from the lockfile's resolved edges, never from re-resolving repodata: a conda `constrains` entry is carried as an `artifact-keeper:constrains` component property rather than masquerading as a dependency, and conda virtual packages (`__glibc`, `__cuda`, `__osx`) — which the parser already records as explained absences, not packages — appear in no document and leak no edges. The root layer ("you asked for pillow") is the document root depending on exactly the in-degree-zero nodes of the emitted graph, which is the recorded project package where the format has one (npm v2/v3, `uv.lock`) and the best available approximation where it does not. Served at `POST /api/v1/sbom/environment?filename=<lockfile name>&format=cyclonedx|spdx` with the raw lockfile as the body; the response carries one document per scope plus the parser's coverage summary, so "we understood 380 of 400 packages" travels with the graphs. Nothing is persisted — the lockfile parser of #4052 is a pure transformation and no stored environment model exists in this build, so documents are regenerated per request (the same shape as the proxy SBOM) and the endpoint needs authentication but no repository permission, since it reads no tenant data.
