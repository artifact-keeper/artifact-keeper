---
section: Fixed
issues: [#5386, #5389]
---
- **MCP capability snapshot history no longer grows without bound, and a stale or duplicate introspection completion no longer stores a snapshot** (#5386, #5389). Every remote probe added a new snapshot row, even when nothing had changed, and the scheduler re-queued every remote of every version of a server every `max(ttlMs, 6 h)`. An unchanged remote therefore added four identical rows a day per version, forever. A snapshot that repeats the newest one of the same version, source and origin (same content hash, outcome and auth state) is no longer stored again: the existing row's new `lastSeenAt` is bumped and it is returned, with no audit, lint or `tool_drift` (`POST .../capabilities` reports this as `created: false`). The scheduler pass now keeps the newest 20 snapshots per version, source and origin and prunes older ones. It never prunes the current snapshot, the drift baseline, a snapshot a `tool_drift` finding names, or the one the newest job of a target points at. Re-probes are queued only for a server's latest version and for versions published in the last 30 days. Migrations 332 (`last_seen_at` column) and 333 (a concurrent index on `mcp_introspection_jobs.snapshot_id`).

  Completing an introspection job also stored the snapshot (and audited it, linted it and raised drift) before ending the claim, and ignored whether the claim was still current. So two concurrent completions of one claim, or a completion racing the lease reaper or a re-claim, could both store a snapshot and a drift finding. The claim check and the snapshot insert now run in one transaction, the side effects run only after it commits, and a late or duplicate completion (or retry) stores nothing and gets `409 mcp_claim_invalid`.
