- **A quarantined or rejected OCI image can no longer be made pullable again by moving its tag** (#5457). Quarantine and rejection state is stored on a manifest's `artifacts` rows, and one image can have several of them: the row for each tag (`v2/<name>/manifests/<tag>`, rewritten in place when the tag moves) and a digest row (`v2/<name>/manifests/<digest>`, written by an MCP pin or a push by digest). The native manifest gate checked a single row picked arbitrarily, and a tag push kept the old hold on the rewritten row. So after an administrator quarantined, or the scanner rejected, the tag's row, an ordinary writer could push another image to the same tag: the original bytes were then served again by digest through hosted and Virtual repositories, and any MCP server version pinned to them was served again too, while the new image wrongly inherited the hold. Native OCI pulls (hosted and Virtual, by tag and by digest) and the MCP backing gate (hosted and Virtual registries, detail and listings) now make the same decision: they check every live row of the digest, and any held row refuses it. When a push moves a held tag, the hold moves to the old digest's row (that row is created if it does not exist, and an existing hold on it is never weakened). The rewritten tag row starts clean for the new image, which still gets its own upload hold. One consequence: an image rejected and then left with no tag keeps a live digest row, so it is retained until an administrator deletes it.
