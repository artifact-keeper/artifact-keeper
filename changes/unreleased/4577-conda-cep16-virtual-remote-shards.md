- **Remote and virtual conda channels serve CEP-16 sharded repodata** (#4577). Sharded repodata (`repodata_shards.msgpack.zst` plus one content-addressed shard per package) was served for hosted channels only; a remote or virtual channel answered 404, so pixi and rattler-based clients fell back to the monolithic index on every solve. For the private-channel pattern, where consumers only ever read a virtual, that meant rebuilding and shipping a 74 MB merged `linux-64/repodata.json.zst` per solve instead of a half-megabyte shard index and a few hundred shards of a few KB each. A remote channel now proxies its upstream's shard index, rewritten so packages and shards resolve against the registry rather than the upstream, and proxies each shard by address through the proxy cache, where it is cached as immutable; a shard that does not hash to its address is refused with 502, never served or cached as that shard. A virtual channel merges its members' shard indexes under the rules of its `repodata.json` merge: hosted members' shards first (one shard per name across all hosted members), then each remote member's index in priority order, a name a hosted member owns never taken from a remote (#4576's ownership guard), and the allowlist applied per package name, with `X-AK-Allowlist-Dropped` counting the names left out. A shard fetched through a virtual is served only when every record in it names a package the virtual admits from a remote, so a hash a client did not learn from the merged index cannot leak a hosted-owned or non-admitted package. Both published upstream layouts work: shards beside the index (conda.anaconda.org) and under `shards/` (prefix.dev), as does an absolute shard host. The sharded endpoints now also follow the repository's read access like every other channel document; a private hosted channel used to answer them anonymously.

  Two limits follow from shards being addressed by their content. A remote package name is listed from the highest-priority remote member that publishes it, so where two remote members publish the same name the sharded view carries the first member's records only (the monolithic index merges them per file). A remote name the allowlist admits only under a version constraint is left out of the sharded view, because a shard carries every version of its package and can be admitted whole or not at all; it stays available through `repodata.json`, where records are filtered one by one. A virtual whose remote member publishes no shard index for a subdir answers 404 for its own, so clients take the documented fallback; a member whose index fetch fails is handled under the virtual's member-failure policy (#4192): 502 naming the member, or a partial index marked `X-AK-Partial-Members` and `Cache-Control: no-store` when the virtual opts in. Shards are still rebuilt per request for hosted channels; materialising them at write time remains #4173.
