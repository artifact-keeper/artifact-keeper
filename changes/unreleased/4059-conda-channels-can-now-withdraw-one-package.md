- **Conda channels can now withdraw ONE package — purge-via-quarantine — with every repodata variant reflecting the withdrawal and a CEP-6 notice explaining it** (#4059). `DELETE /conda/{repo_key}/{subdir}/{filename}` withdraws a single package (malicious upload, license problem, embargoed advisory) without touching the rest of the channel. Withdrawal is deliberately not a hard delete: it applies the same auditable permanent quarantine hold the admin console applies (`quarantine_service::quarantine_now`, #2912), so the row stays in `artifacts` with the reason on it, the existing download gate refuses the package (409), and the hold is reversible through the quarantine console. The repodata gap is closed at the one place every variant is built from: `list_conda_artifacts` now filters through `is_withdrawn`, the exact blocking predicate of the download gate, so repodata.json, current_repodata.json, the bz2/zst/sig encodings, JLAP (its advertised `latest` hash), the CEP-16 shard index and individual shards, run_exports.json and channeldata.json all drop the withdrawn package on the next serve — and the pre-withdrawal content-addressed shard URL stops resolving, so no stale path serves the withdrawn version. The withdrawn package is also named in repodata's `removed` array, the CEP mechanism by which a channel tells clients to evict a package. An expired upload hold stays listed, mirroring the gate. The endpoint sits behind the shared rails rather than a parallel path: the `delete:artifacts` token scope every format-native delete route enforces (GHSA-vvc3-h39c-mrq5) plus the instance-admin gate the quarantine console uses, hosted repositories only, and a blast-radius ceiling by construction — the lookup is an exact-path equality returning at most one row, with no pattern or range form of the endpoint. Each withdrawal appends a CEP-6 channel notice (`{id, message, level, created_at, package, subdir, reason}`, level `warning`) served from `GET /conda/{repo_key}/notices.json` — previously a stub returning an empty array — persisted per repository in `repository_config` under `conda_channel_notices`, so no migration was needed.
