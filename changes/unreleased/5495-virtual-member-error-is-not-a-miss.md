- **A virtual repository whose member fails answers a retryable server error instead of a definitive "not found"** (#5495). Two shapes of the same bug. The Maven virtual checksum walk treated every unsuccessful member fetch alike, so an upstream member answering 5xx, timing out, or refusing the request produced the same `404` as a member that genuinely does not have the coordinate; the walk now distinguishes a miss from a failure and answers `503` when any member failed and nothing else served the file. Separately, the virtual member authorization on the cargo, conda, Debian pool, Go module, npm tarball, PyPI metadata/file and VS Code gallery paths went through the helper that flattens a failed visibility query into the empty member set, which those callers then report as `404` (or, for the gallery, an empty listing); they now use the fallible form, so a database failure surfaces as a server error. Both directions still fail closed: a member the caller may not read is still dropped silently, so member existence is never disclosed.

  This matters because `404` is a definitive answer that package clients cache. Gradle, Maven, Cargo and npm will not re-ask for a coordinate they have been told does not exist, so a few seconds of upstream or database trouble turned into a build failure that persisted long after the cause had cleared. A structural test now requires every client-facing virtual path to authorize through the fallible helper; the OCI blob/manifest walk is the one remaining exemption and names its reason in the source.
