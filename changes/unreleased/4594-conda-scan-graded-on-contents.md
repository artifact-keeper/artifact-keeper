- **A `fail_closed` conda channel no longer locks packages the scanner catalogs nothing for** (closes #4594, follow-up to #4585). The scan-on-proxy gate treated a completed scan that cataloged nothing for the requested `name@version` as inconclusive. That is right for npm, PyPI, RubyGems, Cargo, NuGet and Maven, where the scanner catalogs the package itself, but no bundled scanner catalogs a conda package as a conda component, so for compiled libraries and data packages (`tzdata`, `ca-certificates`) it was the normal result: `fail_closed` answered `423 Locked` for most of conda-forge, and `fail_open` served them `pending` forever without recording a verdict. For `conda` and `conda_native`, a scan that ran to completion over the unpacked archive and cataloged nothing is now graded on its findings (none is `clean`, any is `vulnerable`), stored, and reused like any other verdict, so `fail_closed` serves it with `X-AK-Scan: clean` and `fail_open` serves the next pull `clean`. A scan that could not run is still inconclusive, a package whose `info/index.json` disagrees with its file name is still withheld, and a scan that cataloged a different `name@version` is still inconclusive. Other formats are unchanged.

  Each proxy verdict now records `components_cataloged` (migration 287), returned on `clean` and `vulnerable` items of `GET /api/v1/repositories/{key}/security/proxy-scans`. `0` means the verdict was graded on file contents only; `null` means the scanner reported no catalog, or the verdict predates 1.11.0.
