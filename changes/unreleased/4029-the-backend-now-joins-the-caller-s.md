section: Added
issues: [#4029, #3954, #2414, #2308, #2309]

- **The backend now joins the caller's distributed trace instead of starting its own, and its HTTP entry span is marked `SERVER`** (#4029, part of #3954). A request arriving behind an instrumented reverse proxy produced two unrelated traces: the proxy's, and the backend's. There was no single view of a request end to end, so "how much of this latency was the edge and how much was us" could only be answered by comparing aggregate means from two separate systems. The cause was not that the `traceparent` header was ignored — `api::middleware::tracing` has read it since #2414, but only to slice out the trace-id for use as a correlation-ID string. It was never turned into an OpenTelemetry remote parent, and no `TextMapPropagator` was installed globally at all, so every `extract`/`inject` in the process was a no-op against the SDK's default no-op propagator. `init_tracing` now installs `TraceContextPropagator` on the OTel path, and the `http_request` span adopts a valid inbound context as its remote parent. The span is also now `otel.kind = "server"` rather than defaulting to `INTERNAL`, which is what trace UIs and span metrics use to tell a request entry point from a standalone operation — the same idiom the storage backends already use for their `CLIENT` spans. Extraction fails safe in every direction: a missing, unparseable, wrong-length, non-hex or unknown-version header, and a syntactically valid header carrying all-zero ids (invalid per the W3C spec), all leave the request starting a fresh trace rather than parenting it to nothing. `tracestate` rides along with `traceparent`, except that one over the W3C limits (32 members / 512 bytes) is dropped while the `traceparent` is still adopted — the SDK bounds each key and value but not the list, and copies the parent's `tracestate` onto every span of the request. The `sampled` flag is carried through unmodified. The propagator reads the headers through a local extractor over axum's `HeaderMap`, so this adds no use of the `opentelemetry-http` crate. Operators must configure their reverse proxy or ingress to forward (or originate) `traceparent` for the backend to join its trace; `.env.example` documents this alongside the sampler variables. **No behaviour changes for a deployment with no OTLP endpoint configured**, since the propagator is installed only when tracing is enabled. Under the default sampler (`parentbased_always_on`, see above) honouring a remote parent can only reduce export volume — a caller sending `sampled=00` suppresses its own trace — but under `parentbased_always_off` or `parentbased_traceidratio` an untrusted `sampled=01` can force export. Inbound trace context is currently accepted from any client; a follow-up will gate extraction on the trusted-proxy CIDRs (`rate_limit_trusted_proxy_cidrs`). The correlation-ID behaviour, its 256-byte clamp (#2414) and the single-span invariant that #2308/#2309 established are all untouched — the remote parent is set on the existing `TraceLayer` span rather than by opening a second one.
