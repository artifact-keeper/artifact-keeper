section: Security
issues: [#3977, #1643]
---
- **Bulk promotion now applies the quality gate and the CVE/licence policy per item, which it previously skipped entirely** (#3977). `POST /api/v1/promotion/repositories/{key}/promote` evaluated only the per-pair `promotion_rules` for each artifact: it never called the quality-gate evaluation and never called the promotion policy engine, both of which `POST .../artifacts/{artifact_id}/promote` has always run. An artifact the single-artifact route refuses with `409` on a blocking quality gate, or answers with `promoted: false` on a CVE/licence policy block -- including the `scan_policies.block_unscanned` gate that stops artifacts with no completed security scan (#1643) -- was promoted into the release repository by the bulk route regardless, and an array of one element was enough to take that path. The two evaluations now run per item in the same order the single route uses (gate, then policy, then rules, then the approval consume) and honour the same `skip_policy_check` admin override. A gate or policy block fails **that item** and the batch continues, where the single route refuses the whole request, because a bulk promotion reports per-artifact outcomes so a partial result stays distinguishable from a wholesale refusal; the blocked item carries the gate's message or the policy violations in its own result. Nothing that was promotable before becomes unpromotable unless a gate or policy was already configured to stop it -- an instance with neither configured is unaffected, because both evaluations are no-ops there. Each promoted item's `promotion_history.policy_result` now records the evaluation that ran, in the same shape the single route records, instead of a fixed `{"passed": true, "violations": []}`; and a policy or rule evaluation that errors reports a generic `Policy evaluation failed` / `Rule evaluation failed` reason on that item rather than the raw database error text.
