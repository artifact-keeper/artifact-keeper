section: Added
issues: [#4238]

- **A repository's own administrators can now operate its age gate, and every age-gate decision records the user or service account that made it** (#4238). The age gate is configured per repository but could only be operated by a full instance admin: a principal holding the repository-scoped `admin` verb on its own repository could not turn the gate on or off for it, could not see which of its own packages were pending review, and could not approve one — so every approval became a platform-team ticket, and the instance-wide queue meant whoever approved a package also saw every unrelated team's pending reviews. `GET`/`PUT /api/v1/repositories/{key}/age-gate` now authorize through the same `require_repo_write_access` + `require_repo_admin` chain as every other repository-configuration subresource (`set_cache_ttl`, `set_routing_rules`, `set_upstream_auth`, `update_repo_security`), and a new repository-scoped review queue — `GET /api/v1/repositories/{key}/age-gate/reviews`, `GET .../reviews/{id}`, and `POST .../reviews/{id}/{approve,reject,reopen}` — exposes the same five operations as `/api/v1/admin/age-gate/*` narrowed to that one repository.

  **The grant resolves the same way whether it was given to a person, to a service account, or to a group.** `require_repo_admin` asks `PermissionService::check_permission`, which resolves a `repository:admin` action held directly by the principal, held by any group the principal belongs to, or inherited from the repository's owning project — so delegating repository administration to a team through a group gives that team exactly the operation an individually-granted admin gets, on exactly the repositories the grant covers and no others. Holding `write` still does not suffice: operating the gate is repository configuration, not artifact publishing.

  **Scope is taken from the authorized path segment, never from the query string.** The repository-scoped list ignores any `repository_key` a caller puts in the query, and a review id belonging to another repository answers `404` rather than `403`, so a repository admin cannot widen the queue or probe which review ids exist elsewhere on the instance. `/api/v1/admin/age-gate/*` is unchanged — it remains the unscoped, instance-wide queue behind `admin_middleware` — and an instance admin keeps unrestricted access to every repository-scoped route.

  **A repository administrator can tighten what an instance administrator decided, but only an instance administrator can relax it or hand the policy back.** The age gate is a supply-chain control, and without a guard a repository admin could re-approve or reopen a package an instance admin rejected, or disable a gate an instance admin turned on — which also stops its rejections being honoured, for every virtual that consumes the remote. Migration 244 adds two locks that only an instance administrator's action sets or clears; nothing a repository administrator does changes either one.

  - **Reviews** (`age_gate_reviews.instance_locked`). An instance admin's approval or rejection locks the review: a repository admin may still **reject** it, but not approve or reopen it (a reopened review is pending, and a pending review is honoured once the package ages past the threshold). An instance admin's **reopen releases** the lock — a reopened review is undecided, so the repository's admins may decide it. The lock is part of the decision's compare-and-set, so an instance decision landing mid-request becomes a retryable conflict instead of being overwritten.
  - **Policy** (`repositories.age_gate_instance_locked`). An instance admin's `PUT /api/v1/repositories/{key}/age-gate` locks the policy unless it sends `"instance_locked": false`, which **hands it back** to the repository's admins; a repository admin sending the field at all is refused. Against a locked policy a repository admin may still enable the gate or raise its minimum age, but not disable it, lower the minimum age, or switch the age-source mode. The check runs under the row lock that already serialises policy writes. `GET .../age-gate` now returns `instance_locked`, so a client can explain a refused write before attempting it.
  - **Why a lock and not "last decided by".** A marker would be escaped by tightening first — reject an instance admin's approval to become the last decider, then re-approve. The lock survives the tightening.
  - **Upgrade.** Every decision and configured policy made before this release went through instance-admin-only endpoints, so the migration locks them; hand a policy to its team with `"instance_locked": false`. A repository nobody has configured stays unlocked, and its own admins may set and change its policy freely.
  - The tier follows the actor, not the route: an instance admin acting through a repository route is still an instance admin. The review response carries `instance_locked` too.

  **Decisions now say who made them.** `age_gate_reviews.reviewed_by` was returned as a bare UUID, so the queue could not answer "who promoted this package" without a lookup per row, and a CI service account was indistinguishable from a person; the audit entries for approve, reject and reopen also carried no `actor_name` or `resource_name`, unlike the repository-configuration write next to them, so an age-gate decision reached a SIEM without naming its actor. The review response now carries `reviewed_by_username` and `reviewed_by_is_service_account` alongside `reviewed_by` (hydrated by a `LEFT JOIN users`, the way `promotion_history` already hydrates `promoted_by_username`), and the three audit entries carry the actor name, the repository key and `actor_tier` (`instance_admin` / `repository_admin`). A policy change's `REPOSITORY_UPDATED` entry now also carries `age_gate_change` — the policy it replaced (`previous_enabled`, `previous_min_age_days`, `previous_mode`), the actor's tier, and `relaxed: true` when the change weakened the gate — so disabling the gate or dropping the minimum age is visible in the trail as exactly that, not only as the values it ended at; `backend/schemas/audit-event.v1.schema.json` documents the field. Setting and releasing a lock are distinct actions, `AGE_GATE_LOCK_SET` and `AGE_GATE_LOCK_RELEASED`, each naming the actor, its tier, the repository and the policy or review at that moment — so any relaxation by either tier is identifiable from the log alone: a release, an approve or reopen, or a policy change with `relaxed: true`. The promotion-approval queue gains the same attribution — `requested_by_username` and `reviewed_by_username` on `ApprovalResponse` — shown only to an instance admin or an administrator of the approval's source repository. Those read paths are gated on the source repository's visibility alone, so on a public source repository any signed-in user can read its approvals; everyone else still gets the ids, as before, rather than a way to enumerate the instance's admin and CI accounts. A permission-lookup failure hides the names rather than failing the read. All the new response fields are additive. The four username fields are nullable: `null` for an automatic (unreviewed) row, for an account that has since been deleted (the audit log remains the record of the decision), and — on the approval endpoints — for a caller who does not administer the source repository.
