section: Added

- **A repository's own administrators can now operate its age gate, and every age-gate decision records the user or service account that made it** (#4238). The age gate is configured per repository but could only be operated by a full instance admin: a principal holding the repository-scoped `admin` verb on its own repository could not turn the gate on or off for it, could not see which of its own packages were pending review, and could not approve one — so every approval became a platform-team ticket, and the instance-wide queue meant whoever approved a package also saw every unrelated team's pending reviews. `GET`/`PUT /api/v1/repositories/{key}/age-gate` now authorize through the same `require_repo_write_access` + `require_repo_admin` chain as every other repository-configuration subresource (`set_cache_ttl`, `set_routing_rules`, `set_upstream_auth`, `update_repo_security`), and a new repository-scoped review queue — `GET /api/v1/repositories/{key}/age-gate/reviews`, `GET .../reviews/{id}`, and `POST .../reviews/{id}/{approve,reject,reopen}` — exposes the same five operations as `/api/v1/admin/age-gate/*` narrowed to that one repository.

  **The grant resolves the same way whether it was given to a person, to a service account, or to a group.** `require_repo_admin` asks `PermissionService::check_permission`, which resolves a `repository:admin` action held directly by the principal, held by any group the principal belongs to, or inherited from the repository's owning project — so delegating repository administration to a team through a group gives that team exactly the operation an individually-granted admin gets, on exactly the repositories the grant covers and no others. Holding `write` still does not suffice: operating the gate is repository configuration, not artifact publishing.

  **Scope is taken from the authorized path segment, never from the query string.** The repository-scoped list ignores any `repository_key` a caller puts in the query, and a review id belonging to another repository answers `404` rather than `403`, so a repository admin cannot widen the queue or probe which review ids exist elsewhere on the instance. `/api/v1/admin/age-gate/*` is unchanged — it remains the unscoped, instance-wide queue behind `admin_middleware` — and an instance admin keeps unrestricted access to every repository-scoped route.

  **Decisions now say who made them.** `age_gate_reviews.reviewed_by` was returned as a bare UUID, so the queue could not answer "who promoted this package" without a lookup per row, and a CI service account was indistinguishable from a person; the audit entries for approve, reject and reopen also carried no `actor_name` or `resource_name`, unlike the repository-configuration write next to them, so an age-gate decision reached a SIEM without naming its actor. The review response now carries `reviewed_by_username` and `reviewed_by_is_service_account` alongside `reviewed_by` (hydrated by a `LEFT JOIN users`, the way `promotion_history` already hydrates `promoted_by_username`), and the three audit entries carry the actor name and the repository key. The promotion-approval queue gains the same attribution — `requested_by_username` and `reviewed_by_username` on `ApprovalResponse` — since it had the identical gap. All four fields are additive and nullable: they are `null` for an automatic (unreviewed) row and for an account that has since been deleted, in which case the audit log remains the record of the decision.
