- **A manual MCP Remote sync runs in the background and answers `202`, instead of being cut off by the request timeout** (#5404). `POST /api/v1/repositories/{key}/mcp/sync` ran the whole pass inside the request. Against the official MCP registry a pass often takes longer than `GLOBAL_REQUEST_TIMEOUT_SECS` (120 s), so the caller got `503 Server overloaded, please retry: request timed out`, and the pass was dropped wherever it was, without recording its summary. The trigger now takes the repository's sync lock, starts the scheduler's pass on a task of its own and answers `202 {"repository", "status": "running", "statusUrl"}` at once; the pass finishes whatever happens to the request. `GET .../mcp/sync` adds `running` (a pass of the repository holds its lock, on any replica), and `lastFinishedAt`, `lastError` and `lastSummary` report the pass once it ends. A trigger while a pass runs still answers `409` and starts no second pass. A trigger while scheduled upstream jobs are paused (`upstream_jobs_paused`, #5288) now answers `409` without contacting the upstream, as the scheduled sync does. An unreadable first upstream page, which the trigger answered `502`, is now recorded as the pass's `lastError`.
