- **Scan-on-proxy now gates Debian packages from Debian Remote and Virtual repositories** (#4111, part of #4097). With `scan_on_proxy` on, a proxied `pool/` file, and a `.deb`/`.udeb`/`.ddeb` of a `dists/` or flat layout, goes through the shared inline scan-and-block gate instead of streaming unscanned: a vulnerable package is refused with 403 `scan_blocked`, a clean one is served with `X-AK-Scan: clean`, the verdict is reused for the same digest, and `fail_open`, `fail_closed` and `record_only` behave as for the other enforced formats. The package's own `control` must name the package, version and architecture of the requested file name, and is then graded as itself through a synthetic installed system (an `etc/os-release` and a one-entry dpkg status) on the release the remote's own cached `Release` names, or failing that the release a `+deb12u1` / `~bpo12+1` version names. A package whose metadata disagrees, can be read in more than one way (two `control.tar` members or `control` entries, a field given twice), or whose release cannot be determined is withheld under `fail_closed` (423) without being scanned; source tarballs and diffs are inconclusive the same way, while `.dsc`, `.buildinfo`, `.changes` and every index stream as before. Bytes that disagree with the SHA-256 a cached `Packages` index records are refused with 502. On Remote and Virtual Debian repositories, a pool, `dists/` or flat path containing `?`, `#`, `;`, `\`, a stray `%`, a space or a control character after decoding is now refused with 400. `GET /api/v1/formats` reports Debian as `scan_on_proxy: "enforced"`, and the generic download route refuses a scanning Debian Remote with 403 `scan_on_proxy_route_required`.
